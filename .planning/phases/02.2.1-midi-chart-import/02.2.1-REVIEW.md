# Phase 02.2.1: Code Review Report

**Depth:** standard. Tests were not reviewed beyond scope. No source files modified.

## Summary

The SMF grammar layer is generally well bounded: every read is checked against the chunk end,
the VLQ is capped at 4 bytes, and each loop iteration advances the cursor. The parse choke point
(ChartFile) is clean. The real risks are algorithmic and memory amplification in the Clone Hero
layer, driven by caps that are per list or per track rather than global.

## High

### H-01: Quadratic open-note SysEx range matching hangs the scan on a crafted .mid

**Status: fixed** - linear sweep over tick-ordered gems and disjoint ranges; ranges capped at 4096 per difficulty (MidiChartReader.MAX_OPEN_RANGES). Tests: test_many_open_sysex_ranges_finish_quickly, test_open_sysex_multiple_ranges_sweep_is_exact.

**File:** `src/core/midi_chart_reader.gd:554-563` (caps at `src/core/smf_reader.gd:13,144`)
**Issue:** `_gems` loops over every gem, then over every range in `ranges[di]`. Both are bounded
only by MAX_ENTRIES (300000). `max_entries` on gems is applied later, at lines 398-400, after
`_gems` has run.
**Failure scenario:** A 16 MB file named PART GUITAR holds about 300k Phase Shift SysEx events
alternating start and end with diff=0xFF. That gives about 150k ranges per difficulty. It also
holds 300k note events, about 150k gems in one difficulty. The loop runs about 2e10 iterations of
GDScript, so the scan worker (or the main thread, if the import runs there) freezes for hours.
Dropping the file into Songs/ bricks every launch because the scan re-runs.
**Fix:** Ranges are already in tick order and non-overlapping. Sort the gems by tick (they already
are) and sweep with a single range index, or binary-search the ranges. Also cap SysEx ranges to a
small number (for example 4096) and apply the gem cap before `_gems`.

## Medium

### M-01: Per-track caps allow memory amplification (about 1 GB) from a 16 MB file

**Status: fixed** - file-wide event budget (SmfReader.MAX_EVENTS = 1.5M, limit key max_events) counted across all tracks including delta-0 tracks; exceeding it returns ERR_TOO_LARGE. Duplicate-name track skipping not done (would change which duplicate wins; the budget bounds the cost). Tests: test_global_event_budget_across_tracks, test_all_delta_zero_track_counts_against_budget, test_event_budget_is_global.

**File:** `src/core/smf_reader.gd:13,78-84,121-212`
**Issue:** MAX_ENTRIES caps each list per track, and MAX_TRACKS is 256. There is no global cap.
Every track whose name is in `keep_names` is fully parsed. Duplicate names are allowed, so 256
tracks can all be named "PART GUITAR". A track whose events are all at delta 0 never reaches the
filter check at line 128, because `tick > 0` never becomes true. That track is also fully parsed
and not skipped.
**Failure scenario:** 16 MB at about 4 bytes per note event is about 4M note Dictionaries
(`{tick, pitch, on, seq}`, roughly 200+ bytes each). That is around 1 GB of RAM, so
out-of-memory kills the game while scanning.
**Fix:** Add a global entry budget across tracks, passed through `_Cur`. Fail with
ERR_MIDI_BAD or ERR_TOO_LARGE when it is exceeded. Skip duplicate kept-name tracks once a
candidate has been parsed. Apply the filter at end of track as well as at the first tick > 0
(already done at line 210), and also drop the unnamed tick-0-only tracks early.

### M-02: Per-file parse cost has no time or event ceiling on the main/scan path

**Status: fixed** - MAX_BYTES lowered 16 MB to 4 MB plus the event budget from M-01. Existing size-cap tests reference the constant and stay green.

**File:** `src/core/smf_reader.gd:121-212`, `src/core/chart_file.gd:38`
**Issue:** The parse runs about 4M events through GDScript. `SongScanner.import_folder` calls
`ChartFile.parse` synchronously and `parse_count` is used. If the scan is not threaded for every
caller (song_library `build_chart`, `playtest_driver`), a 16 MB file stalls for tens of seconds.
**Failure scenario:** A hostile or merely huge .mid in the Songs folder freezes Song Select on
Play or Rescan. The 16 MB cap (MAX_BYTES) is far above any real chart (real GH/CH .mid files are
under 1 MB).
**Fix:** Lower the .mid MAX_BYTES (for example 4 MB) or add an event budget (for example 1.5M
total events) after which the file fails.

### M-03: Tick resolution above clamp silently mis-times the chart

**Status: skipped (finding incorrect)** - `res / 3` is the YARG/Clone Hero rule verified in RESEARCH (SustainCutoffThreshold = resolution / 3) and already scales with resolution (one third of a beat at any PPQ); the suggested `res*170/480` is the same ratio only at 480. Added test_sustain_cutoff_scales_with_resolution to lock the behaviour; the clamp is dead but harmless and left as is.

**File:** `src/core/midi_chart_reader.gd:331`
**Issue:** `clampi(division, 1, MAX_RESOLUTION)` is a no-op for any division, because SMPTE
(bit 15 set) is already rejected and the largest possible value is 32767 (below 65535). It is
also never scaled, so the clamp is dead code. It is harmless but misleading. The real issue is
at line 543: `cutoff := res / 3` is an integer divide, and the sustain threshold is not
normalised to Clone Hero's 480-tick basis. For resolution 96, cutoff is 32 (about 1/3 beat),
but for resolution 960 it is 320, so the same musical gap gives different results.
**Failure scenario:** A 96 or 960 PPQ file gets sustain tails on notes that should be plain taps,
or loses real sustains, compared with the same chart authored at 480.
**Fix:** Use `cutoff := res / 3` only if confirmed against RESEARCH D-04; otherwise use
`maxi(1, res * 170 / 480)`, which is Clone Hero's actual rule. Remove or document the redundant clamp.

## Low

### L-01: Bundled signature does not hash .mid content

**Status: fixed** - bundled_signature now hashes .mid; `*.mid` added to export include_filter. Test: test_bundled_signature_follows_mid_content.

**File:** `src/autoload/song_library.gd:302`
**Issue:** `bundled_signature` MD5s only `.chart` and `.ini` files. The comment says it exists to
catch same-size edits. A bundled `.mid` edited without a size change keeps a stale cache entry.
`export_presets.cfg:10` include_filter also lacks `*.mid`, so a bundled .mid would not ship in
the pck.
**Failure scenario:** Bundling a .mid song works in the editor, but the exported build reports a
missing chart; edits keep a stale fingerprint.
**Fix:** Add `ext == "mid"` at song_library.gd:302 and `*.mid` to include_filter if bundling .mid
is intended. Otherwise document that bundling .mid is unsupported.

### L-02: A bad .chart blocks a valid .mid fallback

**Status: fixed** - import_folder retries with the .mid when the picked .chart fails or has no guitar and the .mid is valid. Test: test_broken_chart_falls_back_to_valid_mid.

**File:** `src/core/song_scanner.gd:506-520`
**Issue:** `_pick_chart` only considers .mid when there is no .chart at all. A folder with a
broken or non-guitar notes.chart and a valid notes.mid fails, with no fallback.
**Failure scenario:** A song pack ships both a stub notes.chart and the real notes.mid. The
song shows as broken even though the .mid is playable.
**Fix:** If the picked .chart fails to parse (or has no guitar) and a .mid exists, retry with
the .mid.

### L-03: Trailing garbage chunk rejects the whole file; second name event discarded silently

**Status: fixed (trailing chunk part)** - an overrunning non-MTrk chunk after at least one track now warns and stops instead of failing. The dropped second track-name meta is intentionally left (documented trade-off). Test: test_trailing_junk_chunk_is_tolerated.

**File:** `src/core/smf_reader.gd:75-76,164-170`
**Issue:** An unknown chunk (not MTrk) with an out-of-range length fails the file
(`body + clen > size`), although real files sometimes have junk after the last track. A track
name meta at tick > 0 or a second name meta is dropped from `texts` because the `0x03` branch
catches it first.
**Failure scenario:** A song with a truncated trailing chunk is reported as damaged (ERR_MIDI_BAD)
even though every track was read. This is a robustness trade-off, not a crash.
**Fix:** When the failing chunk is not MTrk and at least one track was already read, break out of
the loop with a warning instead of failing.
