# Phase 02.2.1.1: Code Review Report

**Depth:** standard. Tests were read only for context. The song_scanner, smf_reader and midi_chart_reader changes were outside the file list given.

## Summary

No timing-gate impact. `approach_for`, `depth_for` and `D_FAR` are unchanged and are pinned by `test_beats_visible_unchanged`. All new colours go through Palette, and the fades only scale alpha. No `UiKit.register_fx` regression was found. The packaging scripts are consistent with the embed-pck preset. The defects below are visual or maintainability issues.

## Warnings

### WR-01: Fading lane lines end at full alpha while the cable is still growing

**Fix status:** FIXED (abf87dc). `Highway.fading_line_data` fades the last point by `line_fade(depth_at_y(y_end))`; test added.

**File:** `src/ui/highway.gd:676-678` (`_draw_fading_line`)
**Issue:** The final point is always `col` at full alpha, which assumes `y_end` is at or below the hit line, where `line_fade` is 1.0. `y_end` is `_strip_end_y()` = `lerp(VP.y, STRIP_END_Y, cable_grow)`. During the intro and any time `cable_grow` is below 1, `y_end` can sit at an intermediate depth. That depth is d around 0.5 to 0.9, where the true fade is 0 to 0.9. Rails and separators therefore ramp up to full brightness at the growing tip instead of following the fade curve. Gems and the strip use the true fade, so the growing rails visibly disagree with them.
**Fix:** Use the real depth at `y_end`:
```gdscript
var c_end := col
c_end.a *= Trench.line_fade(depth_at_y(y_end))
_line_cols[n] = c_end
```

### WR-02: `_line_pts` / `_line_cols` are indexed without a guard against use before `setup()`

**Fix status:** FIXED (abf87dc). Scratch arrays removed; the line data is built locally and is safe before `setup()`; test added.

**File:** `src/ui/highway.gd:372-377, 668-675`
**Issue:** The scratch arrays are sized only in `setup()`. `_draw_fading_line` writes `_line_pts[n]` unconditionally. If `_draw` runs on a highway whose `setup` has not happened (for example in a test or tool scene that adds the node first), the write is out of bounds and raises an error. The arrays are also shrunk and re-grown with `resize` on every call, 10 or more times per frame. Both the guard problem and that churn go away if the arrays are sized once.
**Fix:** Declare them with their final size (`PackedVector2Array` filled at declaration or in `_init`), and draw with a count instead of resizing, for example by building local slices. Alternatively, early-return when `_line_pts.size() < LINE_ROW_D.size() + 1`.

## Info

### IN-01: KEEP_OUT_NEAR_D comment is off against the actual geometry

**Fix status:** FIXED (384e1a9). Comment corrected to about 68 px.

**File:** `src/ui/arena.gd:72-73`
**Issue:** The comment says the bottom edge sits 64 px below the hit line. At PERSPECTIVE 0.70, d = -0.071 projects to y of about 998, which is 68 px below `HIT_Y`. A 64 px offset would be d of about -0.067. The old value, d = -0.043 at PERSPECTIVE 1.8, was about 70 px, so the "pixel-derived" claim has never matched exactly. The 4 px difference is harmless for keep-out because it errs on the safe side.
**Fix:** Correct the comment to about 68 px, or derive the constant from `depth_at_y(HIT_Y + 64.0)`.

### IN-02: Shader uniform defaults are stale

**Fix status:** FIXED (b3a23ee). Defaults now 0.70 and 0.35.

**File:** `shaders/sonar_surface.gdshader:36-37`
**Issue:** The defaults are `perspective = 1.8` and `far_spread = 0.045`, while Trench is now 0.70 and 0.35. Highway overrides them, so there is no runtime bug today. Any other consumer or preview of the shader that skips the override would render the old geometry.
**Fix:** Update the defaults to 0.70 and 0.35, or note that they are always overridden.

### IN-03: Sustain fill fade is stepped per quad while the edges fade smoothly

**Fix status:** NOT CHANGED. Needs a visual decision on whether the fade starts are intended; left for human review.

**File:** `src/ui/highway.gd:858-869` (`_fill_ribbon`) and `src/ui/highway.gd:849-854` (`_fade_edge_cols`)
**Issue:** The fill alpha is evaluated once per quad at its midpoint, but the edges use per-vertex colours. Over the fade band, the tube body therefore shows RIBBON_SAMPLES visible alpha steps, and the edge and core lines are smooth. The glow ribbon uses `line_fade` (start 0.45) and the body uses `note_fade` (start 0.85). The glow therefore vanishes well before the body, which may look odd on long sustains.
**Fix:** Build the fill as a polygon with vertex colours (`draw_polygon` with a colour array), or use more samples. Confirm in review that the two fade starts are intended.
