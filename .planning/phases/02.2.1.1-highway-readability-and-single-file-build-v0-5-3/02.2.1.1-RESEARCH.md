## Summary

The whole board is one pure static class, `Trench` (`src/core/trench.gd`, NOT one of the five gated timing-core files). Depth `d` is linear in time (`d = (note_time - vt) / approach`, 0 = hit line, 1 = far end). Everything non-linear lives in four constants: `PERSPECTIVE = 1.8`, `FAR_SPREAD = 0.045`, `VP = (960, 396)`, `HIT_Y = 930`. Screen y is `VP.y + TRAVEL * n(d)` with `n = (s - smin)/(1 - smin)`, `s = 1/(1 + P*d)`, `smin = 1/(1+P)`. [VERIFIED: src/core/trench.gd]

Speed ratio is analytic: dy/dd = TRAVEL * P * s^2 / (1 - smin), so near/far ratio = s(0)^2 / s(1)^2 = (1+P)^2. Today (1+1.8)^2 = **7.84** (matches the README's "about 7.8x"). For ~2.9x, P = sqrt(2.9) - 1 = **0.703**; use **PERSPECTIVE = 0.70 -> ratio 2.89** (inside 2.9 +- 0.2; P range 0.67..0.73 stays in tolerance). Because `APPROACH_BASE = 1.5`, `D_FAR = 1.0` and `depth_for` are untouched, the same beats are visible at 1x and a gem is on `hit_point(lane)` at `d = 0` by construction (`n(0) = 1`, independent of P). Only the *shape* of the curve changes. The far-end widening is `FAR_SPREAD` (0.045 -> about 0.35); the readable far note size falls out of P (s_far 0.357 -> 0.588, note radius 17.9 -> 26.2 px).

Almost every consumer already goes through `Trench.point/scale_at/note_radius` or `Highway.edge_x/depth_at_y` (and the shader gets `perspective`/`far_spread` as uniforms from `Trench`), so the projection change propagates automatically. The work is: (1) change constants + fix tests that hard-code old values, (2) rescale two hard-coded near-depth constants that encode pixel distances (Arena `KEEP_OUT_NEAR_D`, its duplicate in `tests/test_layout_keepout.gd`), (3) add a depth-based fade-in for gems and a far-end fade for lines/glows/sweeps, (4) single-file export.

**Primary recommendation:** Change only `Trench.PERSPECTIVE` (1.8 -> 0.70) and `Trench.FAR_SPREAD` (0.045 -> 0.35, tune by screenshot within 0.30..0.40), add pure static fade helpers on `Trench`, apply them in `Highway`/`NotePainter`/shader, rescale `KEEP_OUT_NEAR_D`, then set `embed_pck=true` and export as `build/UNDERTOW.exe`.

## Architecture Patterns

### Projection data flow

```
song_time + visual_offset -> vt
note.time --depth_for(t, vt, approach)--> d (linear, 0=line, 1=far)
   d --Trench.point(f,d)--> (x,y)   [n=(s-smin)/(1-smin); x = VP.x + f*210*(FAR_SPREAD+(1-FAR_SPREAD)*n); y = VP.y + 534*n]
   d --Trench.scale_at(d)--> s --note_radius(s)=36s+5--> gem radius
   d --NEW Trench.note_fade(d)--> gem alpha          (1 at d<=NOTE_FADE_START .. 0 at D_FAR)
   d --NEW Trench.line_fade(d)--> beat/bar/rail/glow/sweep alpha (1 near, ->0 at far)
screen y --Highway.depth_at_y/edge_x--> strip + rail geometry (inverse of the same formulas)
Trench constants --shader uniforms (perspective, far_spread, ...)--> sonar_surface.gdshader
```

### Pattern 1: Pure fade helpers on Trench
**What:** add two static functions with constants next to `PERSPECTIVE`, so tests and draw code share them.
```gdscript
const NOTE_FADE_START := 0.85   # gem alpha 1 at d <= this; 0 at D_FAR
const LINE_FADE_START := 0.45   # lines/glows full strength at d <= this; 0 at D_FAR

static func note_fade(d: float) -> float:
    return 1.0 - smoothstep(NOTE_FADE_START, D_FAR, d)

static func line_fade(d: float) -> float:
    return 1.0 - smoothstep(LINE_FADE_START, D_FAR, d)
```
Depth units are scroll-speed independent (same fraction of the board at 1x/2x), and `d < NOTE_FADE_START` is exactly 1.0, so the hit zone and Good window (d about +-0.07) are never dimmed. It is a static function of position, not time, so it is correct (and identical) under Low effects and Reduce motion; do NOT gate it behind either (readability, not an effect). [ASSUMED: the 0.85 / 0.45 start values; tune visually.]

### Pattern 2: Gem alpha in NotePainter
`draw_note(ci, type, lane, center, r, state, t, fade)` already has `fade`, but `_draw_normal` only uses it for STATE_MISSED. [VERIFIED: note_painter.gd:198-218] Add the far alpha for the non-missed path (new optional param `alpha := 1.0`, default keeps all current callers and `test_note_painter.gd` valid) and multiply it into the keyline, core, toplight, spec and rim colours with `Palette.alpha(col, a * ...)` / `Color.a *=`. Only take the alpha path when `alpha < 1.0` so the common case allocates nothing extra. `Highway.draw_notes_into` passes `Trench.note_fade(d)`. Chord bars (`draw_chord_bar`) and sustain tubes must multiply the same fade (use fade at the head depth for the bar; for a tube multiply the fill alpha by `note_fade` of its far/head end, or build the ribbon with per-segment alpha, see below). No `Color(...)` literals (tests/test_color_literals.gd); use `Palette.alpha`/`Palette.mix`.

### Pattern 3: Far-end fades for lines, glows, sweeps
- **Strips (Surface Polygon2D):** already per-vertex colours over rows `STRIP_ROW_D = [1.0, 0.7, 0.5, ...]` -> in `strip_color(lane, y, tint)` multiply `col.a` by `Trench.line_fade(depth_at_y(y))`. Add one or two rows between 1.0 and 0.5 (e.g. 0.85, 0.6) so the vertex-colour ramp is smooth. `strip_color` is called by `tests/test_highway_tiers.gd:264` at `Trench.HIT_Y`, where fade = 1, so the existing assertion holds.
- **Separators and rails (`_draw_rails`):** currently `draw_line(a, b, colour, w, true)` with one colour per line. Replace by `draw_polyline_colors(points, colors, w, true)` over rows derived from `STRIP_ROW_D` (edge_x is linear in y, so only colours need the d-based samples) with alpha = base_alpha * `line_fade(d_row)`. Applies to separators, rail, rail glow strokes, flash, MAX core line. `draw_polyline_colors` with antialiasing is supported in the Compatibility renderer. [CITED: docs.godotengine.org CanvasItem.draw_polyline_colors, Godot 4 API; ASSUMED not re-verified on 4.7.2 rendering, check in a screenshot]. Keep the line count small (about 6-8 samples) so draw-call count stays flat.
- **Beat/bar lines (`_draw_beat_lines`):** `d` is already known per line: multiply `beat_col`/`bar_col`/`bar_glow` alpha by `Trench.line_fade(d)`; skip when fade < 0.01.
- **MAX dashes (`_draw_max_dashes`):** `d` known per dash: multiply `col`/`glow` alpha by `line_fade(d)`.
- **Sustain tube glow/tube:** tubes are shaped by `RIBBON_SAMPLES` quads; fade with `_fill_ribbon` per-quad alpha (`line_fade`/`note_fade` of that sample's d) instead of one colour. Core line (`draw_polyline`) -> `draw_polyline_colors`. Keep `ribbon_span` and `TUBE_*` semantic (tests in test_sustain_chord.gd, test_review_fixes.gd).
- **sonar_surface shader:** it already has `d` per fragment and fades lane-edge glass by `smoothstep(0.0, 0.5, n)`. Add `uniform float fade_start` (set from `Trench.LINE_FADE_START`, like the existing Trench uniforms in `_apply_surface_material`) and multiply the sweep band/trail `g` (and phosphor) by `1.0 - smoothstep(fade_start, 1.0, d)`. Shader depth uses `perspective`/`far_spread` uniforms already (so it follows the new P/FAR_SPREAD for free). Scanlines are intentionally left uniform. No colour constants in the shader (VIS-01).
- **Low effects / Reduce motion:** Low removes the shader material (`surface.material = null`) and the glow strokes, so the strip/line fades (vertex colours, alpha math) still apply and the far end stays calm without any effect code. Reduce motion turns the sweep off (`sweep_on`), which the new sweep fade respects automatically. `effect_counts()` keys must stay identical (tests/test_effect_settings.gd enumerates them), so add no new keys.

### Pattern 4: Rescale pixel-derived depth literals
Constants expressed in depth units that really encode pixels must be rescaled by the near-slope ratio (2.8 / 1.7 = 1.647):
- `Arena.KEEP_OUT_NEAR_D = -0.043` (src/ui/arena.gd:72) and `NEAR_D = -0.043` (tests/test_layout_keepout.gd:29): was 64 px below the line; keeping the same pixel bottom edge needs **-0.071**. Update both together or the HUD keep-out test and the colony keep-out disagree. [VERIFIED: values read; recomputed]
- Optional: `gem_depth` missed clamp `-0.06` (draws the missed remnant 90 px below the line; now 54 px) and the `0.06 * approach` ghost timing in `Highway._update_window`/`draw_notes_into`. They are visual only; leave as is unless the missed remnant looks stuck on the line (then -0.10).
- The top edge of the keep-out polygon is `Trench.point(+-2, 1.0)` so it widens from 38 px to 294 px at y 396 automatically; this is the biggest keep-out risk (see Pitfall 3).

### Recommended structure (no new files required)
```
src/core/trench.gd        # P, FAR_SPREAD, note_fade(), line_fade()   (not a gated file)
src/ui/highway.gd         # rails/beat/dash/sustain/strip fades, passes note_fade to NotePainter
src/ui/note_painter.gd    # alpha param on draw_note/_draw_normal, draw_chord_bar alpha
shaders/sonar_surface.gdshader  # fade_start uniform on sweep/phosphor
src/ui/arena.gd + tests/test_layout_keepout.gd  # KEEP_OUT_NEAR_D / NEAR_D
tests/test_trench.gd      # new ratio + fade tests, far-convergence test updated
```

### Anti-patterns
- Changing `APPROACH_BASE`, `D_FAR`, or `depth_for` (would alter beats visible / timing semantics).
- Editing `conductor.gd`, `clock_model.gd`, `input_judge.gd`, `hull_score.gd`, `judge_config.gd` (timing gate fails, `tools/check_timing_gate.ps1`).
- Fading by time/animation (breaks Reduce motion and test determinism); fade by depth only.
- `Color(r,g,b,a)` literals in draw code (test_color_literals).
- Registering new fx owners (not needed; the existing `Highway` registration covers it).

## Common Pitfalls

### Pitfall 1: Touching the timing semantics by accident
**What goes wrong:** editing `APPROACH_BASE`/`D_FAR` or the visual-offset convention changes beats visible or the on-line moment. **Avoid:** change only `PERSPECTIVE`, `FAR_SPREAD`, add fade helpers. **Detect:** `test_visual_sync.gd` (60 positions), `test_trench.gd` approach tests, `tools/check_timing_gate.ps1` prints TIMING GATE OK.

### Pitfall 2: Rescaled depth constants forgotten
Missed-remnant clamp and Arena `KEEP_OUT_NEAR_D` encode pixels (Pattern 4). Forgetting the test duplicate (`NEAR_D`) leaves the HUD test checking a different polygon than Arena avoids.

### Pitfall 3: Wider far end vs HUD/colony keep-out
The keep-out trapezoid top goes from 38 px to about 294 px wide at y 396 (then +48 px margin). Streak counter, section banner, hull arc or the Arena colonies near the vanishing point can now intersect. **Avoid/detect:** run `test_layout_keepout.gd`, `test_hud_gauges.gd`, `test_overlay_layout.gd`, `test_arena.gd` early (right after the constants change) and adjust `FAR_SPREAD` down (0.30) before moving HUD elements. HUD layout moves are out of scope; if a conflict is found at 0.35, lower FAR_SPREAD first and report.

### Pitfall 4: Far gems merge anyway
With larger far radius (26 px) and 73.5 px lane pitch, same-time chords at the far end nearly touch. Verify with a screenshot of a dense chord section; if too tight raise FAR_SPREAD to 0.40 (lane pitch 84 px) rather than shrinking the note.

### Pitfall 5: Antialiased polyline colour and Compatibility renderer
Verify rails with `draw_polyline_colors(..., true)` visually; fall back to splitting each rail into 3-4 `draw_line` segments with stepped alpha if the gradient looks banded.

### Pitfall 6: Strip fade breaks `strip_color` contrast assumptions
`test_contrast.gd` / `test_highway_tiers.gd` check strip colours near the line, where fade = 1. Do not apply fade below `LINE_FADE_START`.

### Pitfall 7: Single-file export gotchas
- `export_presets.cfg` currently has an uncommitted change by another agent adding `*.mid` to `include_filter` (`git diff` shows it). Keep it; edit only `embed_pck` and `export_path`.
- The exported name must be `UNDERTOW.exe` (README says so). The preset `export_path` is `build/undertow-debug.exe` and `tools/export.ps1` hardcodes `undertow-debug.*` names in three places.
- `dist.ps1` currently copies the `.pck`; with embed there is none and `Test-Path` on it would abort the build.
- `user://` path comes from `config/name` ("UNDERTOW"), unchanged, so settings/scores/calibration carry over from older builds.

## Perf (D-05 neighbours, scenario `perf`)

`tools/playtest/run_all.ps1 -Scenarios perf` (`sc_perf`, windowed, 1920x1080 forced, 30 s on the densest bundled window, Full and Low) gates `p95 <= 4.35 ms` (PERF_P95_GATE_MS). Expected cost of this phase is negligible: fades are a few float ops per visible gem/line (only about 5 gems are inside the fade band), rails go from 2+ `draw_line` per rail to one `draw_polyline_colors`, tube ribbons already issue `RIBBON_SAMPLES` quads (per-quad colour is free), shader adds one `smoothstep` per fragment on the strip only. Wider far lanes enlarge the strip area slightly (about 4 polygons). Keep allocation out of `_draw` (reuse `PackedVector2Array/PackedColorArray` members, as `_edge_l`/`_quad` do).
