## Summary

The pipeline that worked on all three songs is: **decode the MP3 with libsndfile (bit-identical timing to Godot's decoder) → htdemucs (4 stems, about 22 s CPU per song) → beat_this (beats and downbeats, about 2 s) → grid repair, smoothing and phase correction → onsets on the chosen stem with a backtracked spectral-flux "attack start" detector, kept only if the mix also has an attack within ±30 ms → strength-ranked density cap → snap → pitch per note from Basic Pitch (ONNX, about 1 s) with octave folding → contour lanes.** Note *timing* comes from the stem's onsets. Basic Pitch is used only for *pitch*: its own note onsets are frame-quantized, often early, and fire on accompaniment. Pipeline A (Basic Pitch onsets) reached only 24–61% of notes within ±25 ms of a mix onset. Pipeline B (stem onsets) reached 60–97%. The recommended pipeline (B + audibility filter + phase-corrected grid) reached **99.5% on Sea Shanty 2, 90.9% on HRT ("other"), and 81.1% on INVISIBLE ("other")**, all with a median error of −2.1…0.0 ms. Chance level is 17–30%.

Three findings change the plan. (1) **Demucs 4.1.0 decodes the MP3 itself with `sphn`/symphonia, and its stems come out exactly 25.01 ms (1103 samples) LATER than Godot's stream.** libsndfile/mpg123 matches Godot within 0.05 ms. Always decode once with `soundfile`, write a WAV, and give demucs the WAV. (2) **beat_this outputs beats on a 20 ms frame grid, and they land 7–12 ms after the audible attack** (seen on all 3 songs and on the Neversoft map). The tempo map needs a phase-correction step, and SPEC req 2's "tracker beats" must mean the *refined* beat list. (3) The Neversoft professional chart itself only puts **54.5% of Expert notes within ±25 ms of a guitar-stem onset (chance 37.7%) and 73.5% for the mix (chance 43.1%)**, with median −2.0 / +5.9 ms. The SPEC fixed gate (90% / 80%) is therefore *stricter* than the professional baseline. Our charts meet the fixed numbers on all three songs, INVISIBLE only just. The stem metric is near 100% by construction, because the notes come from the same kind of stem onsets, so it checks the plumbing and is not independent evidence. The mix metric, the chance level and the ear check are the meaningful evidence.

**Primary recommendation:** Build `tools/autochart/` as a Python 3.12 (uv) CLI with these pinned packages: torch 2.11.0+cpu, demucs 4.1.0 (`htdemucs`), beat-this 1.1.0, librosa 1.0.0, soundfile 0.14.0. Add a second Python 3.10 venv for basic-pitch 0.4.0 + onnxruntime, called as a subprocess. Sea Shanty 2 and INVISIBLE use the htdemucs "other" stem. HRT uses "other" (melodic synth), filled from drums where "other" is silent, with drums-only as the recorded fallback.

### Beat tracker vs Neversoft's hand tempo map (603 beats, 122.7–151.5 BPM)
| Tracker | med \|e\| | p90 \|e\| | signed median | within ±70 ms |
|---|---|---|---|---|
| beat_this final0 (mix) | 17.0 ms | 44.0 ms | **+12.0 ms** (late) | 97.2% |
| beat_this, minus a global 12 ms | 13.0 | 39.8 | 0.0 | 96.8% |
| librosa beat_track | 30.5 | 166.0 | +19.6 | 80.9% |

Per 30 s window, the Neversoft map *itself* wanders −1.6…+12.9 ms against the drum attacks (beat_this: −3…−17 ms). Part of the 17 ms disagreement is the hand map. The robust finding is that beat_this's beats sit on 20 ms frames and lag the attacks. On our songs, a local phase fit to mix attacks moved the beats by −6.5 / −10.5 / −2.4 ms (Sea Shanty / HRT / INVISIBLE). beat_this doubles the tempo in some sections (BIF 180–210 s: 300 BPM). The repair step must merge half-beat IBIs.

What this means: on distorted metal guitar, an automatic onset chart matches about 57% (F) of a human chart's note times. The human chart simplifies chugs and the stem contains both guitars. This matches STRUM's self-reported 65% guitar F1 at ±100 ms. Our songs are far cleaner (Sea Shanty mix match 99%). Do not set an F-score target against human charts. Use the sync gate and the ear check.

### End-to-end CPU per song (recommended pipeline)
soundfile decode about 1 s + htdemucs 21–25 s + beat_this 1.3–1.8 s + D3 onsets on stem and mix 2–4 s + Basic Pitch about 1 s + sections 1–5 s, so **about 30–40 s per song** on the 9800X3D. Model download on the first run: about 80 MB (htdemucs) + 77 MB (beat_this).

## Chosen Pipeline

1. **Decode**: `soundfile.read(song.mp3)` → mono/stereo float WAV at 44.1 kHz → `build/autochart/<id>/decoded.wav`. Cross-check: correlate it against Godot's decode (harness `align_<id>_decoded.wav`, which is 48 kHz, so resample first). |lag| must be ≤ 1 ms, else abort.
2. **Separate**: `python -I -m demucs -n htdemucs -d cpu -o … decoded.wav`. Feed the **WAV**, never the MP3. All 4 stems are kept for STEM-04.
3. **Beats**: `beat_this.inference.Audio2Beats("final0", device="cpu", dbn=False)` on the mix → repair (drop IBI < 0.6 P, split IBI ≈ k·P) → local linear smoothing (±8 beats) → phase correction to mix attack starts (median residual of D3 mix onsets to the beat grid). Use a **global** correction for constant-tempo songs (local correction made Sea Shanty wobble 195–205 BPM), and a smoothed local one otherwise. Downbeats from beat_this. Use 4/4 unless ≥ 2 consecutive bars agree on another count.
4. **Notes (timing)**: D3 onsets on the chosen stem (delta 0.05) → keep only onsets with a mix attack within ±30 ms (D3 on mix, delta 0.03) → rank by onset strength and keep the strongest down to the target density (Expert about 3–4 n/s) → silence gate (stem RMS 50 ms > −35 dB re 95th percentile) → merge < 1/16 (keep the stronger) → snap to 1/16 or 1/12 if ≤ 15 ms → cap 8 notes per 1 s window.
5. **Pitch**: Basic Pitch (venv B) on the stem → for each note, the highest BP pitch starting within ±50 ms, else the highest sounding at +30 ms, else none (fall back to spectral centroid).
6. **Lanes**: SPEC contour rule on **octave-folded** intervals `d' = ((d + 6) mod 12) − 6`. Sea Shanty lane steps without folding: repeat/±1/±2 = 21/41/38%. With folding: 35/56/9% (reference 28/50/19).
7. **Reductions, sections, solo, preview, write, gate**: §Architecture Patterns.

### Pattern 1: Per-beat tempo map with error diffusion
**What:** One `B` per beat (SPEC req 2, as in the Neversoft reference), 192 ticks per beat. B = milli-BPM, rounded with the rounding error carried into the next beat, so cumulative drift stays in microseconds (measured: ≤ 0.0016 ms at the last beat on all 3 songs).
```python
# Source: build/research/scripts/tempo_gate.py (measured)
t = beats[0]; err = 0.0; events = []
for i in range(len(beats) - 1):
    ibi = beats[i + 1] - beats[i]
    mb = round(60000.0 / ibi + err); err += 60000.0 / ibi - mb   # milli-BPM
    events.append((first_beat_tick + 192 * i, mb))              # "  <tick> = B <mb>"
```
Lead-in: chart time 0 = audio 0 (delay 0, since our time base is Godot's). Bar 1 = first downbeat. Ticks before it = `n = round(first_downbeat / IBI)` beats at `B = 60000·n / first_downbeat`. If n = 0 (downbeat < half a beat, e.g. Sea Shanty 0.06 s), put the downbeat at tick 0 and set `delay = round(first_downbeat·1000)` ms. Importer limits are 1–2000 BPM (`chart_importer.gd` MIN/MAX_BPM).

### Pattern 2: D3 "attack start" onset detector (also the gate detector)
librosa onset_strength (n_fft 2048, hop 64 = 1.45 ms, lag 1, max_size 3) normalised by its 99th percentile → `peak_pick(pre_max=post_max=30 ms, pre_avg=120 ms, post_avg=30 ms, delta, wait=30 ms)` → move each peak back to where the 1 ms RMS envelope first crosses 50% between the preceding minimum (≤ 30 ms before) and the peak. Code: `build/research/scripts/lib.py::onsets_gate`. Why backtrack: flux peaks land 4–17 ms after the audible start (Neversoft notes vs mix: flux +17 ms, attack-start +0.8 ms). Humans chart the attack start. This detector puts the Neversoft notes at −2.0 ms on the guitar stem and +5.9 ms on the mix.

### Pattern 3: Audibility filter
Keep a stem onset only if the mix (Godot decode) has a D3 attack (delta 0.03) within ±30 ms. This is "every note has a sound you can hear" made measurable. Effect on mix match: HRT other 85.3 → 90.9%, INVISIBLE other 74.9 → 81.1%, HRT bass 75.9 → 88.1%. Sea Shanty is unchanged (already 99.5%).

### Pattern 4: Grid phase correction
`corrected(beats, mix_onsets)`: shift beats by the median residual of nearby attacks to the grid (|r| < 30 ms). Constant-tempo song: one global median. Others: local median over ±8 beats, then re-smooth before writing B events. Sea Shanty on-grid share went 75 → 86%.

### Pattern 5: Reductions keep Expert ticks
Hard/Medium/Easy select subsets of the Expert note *indices* (never new times). Targets from the SPEC reference table: keep Hard 90–100%, Medium 65–75%, Easy 45–55%. Priority: downbeat > beat > 8th > 16th/triplet, then onset strength, then phrase starts (first note after a ≥ 1 beat gap). Easy re-runs the contour on the kept notes with lanes 0..2. Chords: Hard keeps ≤ 2-note, Medium keeps ≤ 3% of notes as 2-note on downbeat accents, Easy none.

### Pattern 6: Chart writing (STEM-05)
Write `N <lane 0..3> <len>`. Gems 0–3 map to lanes 0–3 under `_collect` (identity). Do not write 4 (Orange merges into lane 3) or 7 (open becomes a chord). Sustain lengths ≤ 48 ticks (a 16th at 192) are turned into taps by the importer (`SUSTAIN_TAP_DIVISOR 4`), so only write sustains > 1 beat (SPEC), shortened by 1/16. Output deterministic text: sorted events, `\r\n` or `\n` fixed, no timestamps, so hashes are stable (SONG-05).

### Pattern 7: Sections / solo / preview
Beat-synchronous chroma_cqt + MFCC per *bar* → `librosa.segment.agglomerative(F, k = duration/20 s)`. HRT boundaries came out every 22.3 s = 8 bars, which is plausible. 1–5 s CPU. Name them generically (D-08). Solo = the densest 4–8 bar window with ≥ 16 Hard notes. Preview = start of the loudest section (mean RMS). Confidence MEDIUM: boundaries are not ear-checked.

### Pattern 8: STEM-04 instrument lanes (cheap)
htdemucs already gives drums/bass/other/vocals. Run Pattern 2–3 per stem, assign stem k to lane k, and merge with the same cap/merge rules. Lane = instrument, so no contour. About 2 s extra per song. Plan it after STEM-06/07 as the SPEC says.

### Anti-Patterns to Avoid
- **Letting demucs decode the MP3**: stems are 25 ms late against the game.
- **Using Basic Pitch onsets for note timing**: 24–61% mix match, early by 4–20 ms.
- **Writing raw beat_this beats as B events**: 20 ms quantization gives per-beat tempo jitter (one frame on a 300–700 ms IBI is ±3–7%) plus a 7–12 ms late bias.
- **Gating against the same detector that produced the notes without a chance level**: always print chance, plus the mix metric.
- **librosa beat_track as the tempo source**: octave errors (Sea Shanty 100 vs 200 BPM).

## Common Pitfalls

### Pitfall 1: Decoder padding mismatch (+25.01 ms)
**What goes wrong:** Charts land 25 ms early against what the player hears. **Why:** demucs 4.1.0 reads MP3 through sphn/symphonia, which does not apply the LAME gapless trim the way mpg123/Godot do (lag exactly 1103 samples ≈ 576 + 529). **Avoid:** decode with soundfile first and feed WAV. Assert the lag ≤ 1 ms against the Godot decode. **Warning sign:** the gate median is about −25 ms.

### Pitfall 2: beat_this frame quantization and late bias
**What:** Beats on a 20 ms grid, 7–12 ms late vs attacks. **Avoid:** repair → smooth → phase-correct (Pattern 4). Compare the SPEC req-2 tempo gate against the **refined** beats stored in `beats.json`. Against raw beat_this beats, HRT measures p90 21.2 ms (fails ±20) only because of the deliberate −9.5 ms correction. Against the refined beats it is 0.00 / 0.00 ms. Record both. **Spec note:** SPEC req 2 says "tracker's beats". Interpret it as the refined beat list and write that interpretation in the README.

### Pitfall 3: Local phase correction wobbles a constant tempo
Sea Shanty (MIDI, exactly 200.000 BPM) became 195–205 BPM after a per-beat local correction. Detect constant tempo first (linear-fit residual p90 ≤ 2 ms after repair), then use one B and a global offset.

### Pitfall 4: `align` harness hangs on the new songs
`sc_align()` loops `while frames.size() < n` with `n = ceil(stream.get_length() * rate)`. For HRT and INVISIBLE, Godot's MP3 playback returns fewer frames than `get_length()` promises (HRT: 7,138,304 frames returned vs 161.876 s length), so `mix_audio` returns empty arrays forever. A headless decode script with the same loop hung for 5 minutes. Sea Shanty completed. **Fix (tools/playtest, not game code):** break when `mix_audio` returns 0 frames, or loop on `pb.is_playing()`. Use the actual decoded length for `song_length`.

### Pitfall 5: The ±25 ms percentage depends on density
At 13 onsets/s, randomly placed notes score about 60%. Always print chance (random ±60–200 ms shifts) next to the metric. Use detector delta 0.1 for the gate (8–10 onsets/s on dense stems).

### Pitfall 6: Basic Pitch octave errors and skyline layer switching
The Sea Shanty interval histogram has 126 exact octaves out of 437 intervals. **Avoid:** octave-fold intervals before the contour rule. On INVISIBLE, "other" BP pitches jump between B2/B3/B4 (bass bleed), and folding fixes that too.

### Pitfall 7: Python environment traps
- basic-pitch 0.4.0 on Windows with Python ≥ 3.11 requires tensorflow < 2.15.1. Use Python 3.10 so it takes onnxruntime.
- resampy 0.4.2 needs `pkg_resources`, so pin `setuptools<81`.
- librosa 1.0.0 needs Python ≥ 3.12 (venv A).
- torchaudio 2.11 pins torch 2.11 (latest torch is 2.14.1). Install both from the CPU index together.
- `python -I` ignores `PYTHONIOENCODING`. Windows cp1252 consoles crash on `♯` from `librosa.midi_to_note`. Use `unicode=False`.
- HF hub warns about symlinks on Windows (harmless). Set `HF_HUB_DISABLE_SYMLINKS_WARNING=1`.
- `slopcheck install` installs packages. Use `slopcheck scan`.

### Pitfall 8: Godot headless mix rate is 44.1 kHz, windowed is 48 kHz
`align_<id>_decoded.wav` from the windowed harness is 48 kHz. Resample (soxr) or compare in seconds. Never compare sample indices across rates.

### Pitfall 9: Density targets vs sparse stems
INVISIBLE/HRT "other" reach only 2.2–2.6 n/s after the audibility filter, below the 3–5 n/s guide. Do not lower the filter to hit density. Instead fill silent bars from a second stem at section boundaries (SPEC allows bass for INVISIBLE). Record the per-song density in the README.

### Realign check (decoder lag)
```python
# Source: build/research/scripts/offsets.py (measured -0.05 ms soundfile, +25.01 ms sphn)
from scipy.signal import correlate
def lag_ms(ref, x, sr=44100, seg=(20.0, 50.0), maxlag=0.2):
    a = ref[int(seg[0]*sr):int(seg[1]*sr)]; m = int(maxlag*sr)
    b = x[int(seg[0]*sr)-m:int(seg[1]*sr)+m]
    c = correlate(b, a, mode="valid", method="fft"); k = int(c.argmax())
    return (k - m) / sr * 1000
```

| V5 Input Validation | yes | Input audio is untrusted. Decode only via soundfile/libsndfile. Validate the sample rate and length. The generated `.chart` goes through the existing importer limits (BPM 1–2000, int parsing ≤ 12 chars) |

| Threat | STRIDE | Mitigation |
|---|---|---|

| Crafted audio crashing the decoder | DoS | Dev-only, offline. Acceptable |
