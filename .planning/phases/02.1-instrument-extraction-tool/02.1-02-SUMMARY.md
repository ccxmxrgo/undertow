# Phase 02.1 Plan 02: Tempo map, Expert quantizer and chart writer Summary

Stdlib-only deterministic core of the autochart pipeline. Refined beats become a per-beat `[SyncTrack]`, using absolute-time error diffusion and the importer's own tick-to-time math. Onsets become Expert notes on the grid: density target, merge below 1/16, snap to 1/16 or 1/12 within 15 ms, 8 notes/s cap. Both are written out as golden-tested, byte-stable `.chart` and `song.ini` text with lanes `N 0..3` only.

## What was built

- **tempo_map.py**: `build_tempo_map(beats, downbeats, constant_tempo, resolution=192)` builds the lead-in (n = round(fd/IBI); n = 0 sets the delay, n >= 1 adds a lead-in B at tick 0). It writes one B per beat, or a single least-squares B for constant tempo, and puts TS at a downbeat only when at least 2 bars in a row agree. `tick_to_sec`/`sec_to_tick` mirror `ChartImporter._segments/_tick_to_sec`: BPM clamped to 1..2000, the last B at one tick wins, 120 BPM before the first B, delay added. Segments are cached with `lru_cache`.
- **quantize.py**: `build_expert(onsets, tm, target_nps, cap_per_s=8, snap_ms=15)` runs rank, merge, snap, post-snap collision merge, then the sliding 1 s cap (drops the weakest note in the densest window). The output Note records follow the shared contract (`tick, t, t_onset, snap, end_tick, lanes=[], len=0` plus pass-through fields). The input dicts are not changed. Speed: 4000 onsets with a 500-beat map run in about 0.24 s. Also adds `notes_per_window_max` and `on_grid_share` for reports.
- **write_chart.py**: `render_chart(song, tm, sections, tracks, solo)` and `render_ini(meta)`. The format copies `songs/synth_wave_april/notes.chart`: LF, two-space indent, `E solo` before N lines at the same tick and `E soloend` after, lanes ascending.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in plan spec] The 2 us per-beat bound can't be reached with integer milli-BPM at slow tempos**
- **Found during:** Task 1
- **Issue:** The plan's behavior and must-have asked for max |tick_to_sec(beat) - beat| <= 0.000002 s over 200 beats at about 86 BPM. One milli-BPM step at 86 BPM changes a beat's length by about 8.2 us. So any one-B-per-beat map has up to about 4.1 us error on some beats, whatever the rounding strategy. RESEARCH's "<= 0.0016 ms" was measured only at the last beat.
- **Fix:** I used the best possible scheme: per-beat optimal integer milli-BPM on absolute time, with no drift. The test now checks max error <= the half-step bound 30000/mb^2 s and < 5 us. Measured: max 4.05 us, median 2.26 us, last beat 2.87 us. That is far below the SPEC acceptance of ±10 ms median / ±20 ms p90.
- **Files modified:** tools/autochart/tests/test_tempo_map.py, tools/autochart/stages/tempo_map.py
- **Commits:** 6c73ef0, 44fb600

**2. [Rule 1 - Test data] The snap-to-1/12 case used 200 BPM**
- **Found during:** Task 2
- **Issue:** "5 ms from a triplet line and 20 ms from the 1/16 line" can't happen at 120 BPM: the closest triplet and 1/16 lines are 41.7 ms apart there.
- **Fix:** That case uses a 200 BPM map (lines 25 ms apart): the onset at 0.095 s is 5 ms from 1/12 and 20 ms from 1/16, and gets snap "12". The 12-notes-in-1-s cap test uses 240 BPM, so 1/16 spacing survives the merge.
- **Commit:** d074f55

**3. [Rule 2 - Correctness] Post-snap collision merge and pickup-bar TS** (both are recorded under decisions above).
