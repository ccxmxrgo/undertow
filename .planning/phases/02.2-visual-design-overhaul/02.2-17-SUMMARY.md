# Phase 02.2 Plan 17: Album art and detail panel top half Summary

Song Select now shows a cover for every song. If the song folder has `album.png` or `album.jpg` next to its chart, that art is loaded on a worker thread and fades in over 180 ms. Otherwise a deterministic generated cover is shown at once: an abyss gradient picked from the title's sha256, four faint sonar arcs with gaps from one corner, and the title's initials. Zipped songs now keep their png/jpg, and old zip caches re-extract once so they get art too. The detail panel's top half follows UI-SPEC 6:
- the 256 px chamfered cover with SONAR edge and brackets
- an Oxanium title (2 lines + "..."), artist and CHARTED BY
- LENGTH / BPM / NOTES in SONAR
- the divider at y 424
- best depth (gold), accuracy (one decimal) and the grade letter in its grade colour

## What was built

### Task 1 (TDD: f6578c3 test, 2c073bf feat)
- **AlbumCover** (UI-SPEC 4.10):
  - The lookup uses only `album.png` then `album.jpg` in `chart_path.get_base_dir()`. No other names, no ini paths, no parent folders.
  - `load_art_image` checks, in order:
    - the 8 MB cap (file length, before reading)
    - PNG/JPEG magic bytes
    - header dimensions (<= 4096)
    - the decode result
    - post-decode bounds
  - It then centre-crops to a square, downscales to <= 512 and drops mipmaps.
  - `generated(title)` returns a 512x512 RGB8 cover: the gradient pair is sha256 byte 0 mod 8 from `Palette.COVER_GRADIENTS`, the arc corner is byte 1, and the arc phase is bytes 2..3. The arcs are r 80/140/200/260, 2 px, SONAR 14%.
  - `initials` gives "SS", "H" and "?".
  - `request()` loads on the WorkerThreadPool. The texture is created on the main thread. The LRU holds 32 entries, and concurrent requests for one id coalesce. `reap` / `shutdown` reap the worker tasks the same way the preview loads are reaped.
- **ZipExtractor**: png/jpg/jpeg are allowed. Each image entry has an 8 MB cap; a larger image is skipped. The safe_rel traversal checks are unchanged.
- **SongScanner**: the `.done` marker now stores `EXTRACT_VERSION` "2". The old "ok" marker triggers `_rm_tree` and a re-extract once.
- **Fixture**: `tests/fixtures/album_art/album.png` is a 64x48 image I generated with a one-off headless script (ABYSS_700 / SONAR halves). It is first-party. `.gdignore` keeps Godot from importing it.
- **Tests**:
  - tests/test_album_cover.gd has 16 cases:
    - fixture crop to 48x48 with pixel checks
    - missing file, jpg fallback and png-first order
    - downscale to 512
    - the 8 MB cap
    - over-4096 PNG and JPEG
    - garbage and truncated PNG
    - the lookup rule
    - determinism and title normalisation
    - the gradient pair from the hash, the arcs drawn and the initials
    - same id decodes once, misses cached, LRU eviction with touch, and the generated texture cache
  - tests/test_song_errors.gd:
    - the allow-list test now expects album.png to be kept
    - new image size-cap and traversal case
    - new old-marker re-extract case

### Task 2 (97d7e03)
- **SongSelect**:
  - Owns an AlbumCover and requests art only for the selected song: on a selection change, filter changes included, but not when the id is unchanged. Stale results are ignored by song id.
  - Paints the cover through `draw_polygon` with UVs, so the image itself carries the TL/BR chamfer.
  - The title block, stats and best values sit at the UI-SPEC 6 coordinates, in Palette tokens.
  - The DIFFICULTY caption moves to baseline 456. The tiles stay at y 488 until plan 18 restyles them.
  - List, filter, sort, scan and model code are unchanged.
- **Harness (sc_songs)**: the fixture library gets first-party art: a lane-band PNG inside "Zipped Song.zip" and a JPG in "Ebb Tide". New checks:
  - "bundled song shows the generated cover"
  - "zipped song keeps its album.png and shows it as art"
  - "best values: depth, accuracy and grade"
  - "folder album.jpg shows as art"
  - "corrupt album.png falls back to the generated cover" (the community fixture's 4-byte album.png)

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] Header dimension check before decoding**
- The plan rejects > 4096 "after load". An 8 MB PNG can still decode to gigapixels, so the PNG IHDR or JPEG SOF dimensions are now checked before decoding. The post-decode check stays as well.
- **Commit:** 2c073bf

**2. [Rule 2 - Security] Decoder chosen by magic bytes instead of `Image.load_from_file`**
- `load_from_file` picks the decoder by extension. The file is now read once (already length-checked), sniffed, and decoded with `load_png_from_buffer` / `load_jpg_from_buffer`. These are the same built-in decoders.
- **Commit:** 2c073bf

**3. [Rule 1 - Bug] Flaky directory-count assertion in the new cache-marker test**
- **Found during:** full-suite run (798 cases, 1 failure; it passed alone).
- **Issue:** the test counted folders under the zip cache root. A background library scan from another suite can unpack into the shared static `zip_cache_root` while the test runs.
- **Fix:** the test locates its own cache folder from `entry.chart_path.get_base_dir()`.
- **Commit:** b1750b1

**4. [Scope] Harness evidence added to tools/playtest/playtest_driver.gd**
- This file is not in the plan's files_modified list. It was needed to prove the "art" path end to end (zip png, folder jpg) and to give the plan's songs-scenario verification something to check.
- **Commit:** 97d7e03

**5. Interpretation: "never during a scan"**
- Besides the scanner never loading art, Song Select defers an uncached cover request while `library.scanning` and issues it when the scan ends.
