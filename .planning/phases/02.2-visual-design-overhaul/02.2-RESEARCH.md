# Phase 2.2: Visual Design Overhaul - Research

**Researched:** 2026-10-10
**Domain:** Godot 4.7.2 GDScript 2D UI/rendering (Compatibility renderer): `_draw`-based board, Control/Theme screens, CPUParticles2D, canvas_item shaders, harness and tests
**Confidence:** HIGH for the codebase map and the Godot API facts (checked in a scratch Godot 4.7.2 project this session). MEDIUM for the perf-gate method (measured on this machine, but the display was at 60 Hz during research).

## Summary

Almost every screen in UNDERTOW is built **in code**. Each `.tscn` in `scenes/` is a single root Control with a script, and every node is created in `_ready`/`setup`. Two kinds of drawing are mixed. (1) **Pure `_draw` canvases**: `Highway`, `Arena`, `Hud` (arc and badges), `Feedback`, `StreakCounter`, `GogglesIntro`, `StepSlider`, `RebindCell`, and Song Select, which is about 1,500 lines of hand-painted `Pane` callables. (2) **Theme-driven Controls** for menus and overlays: `MainMenu`, `ResultsScreen`, `FailScreen`, `PauseMenu`, `ConfirmDialog`, `SettingsScreen`, `CalibrationWizard`, all styled by `ui/undertow_theme.tres` (terminal green) plus `Palette` overrides. Colour literals are spread across 8 `src/ui` scripts, 60 in total. `Palette` is already the token hub, so the design-system work is an in-place migration rather than an introduction. The UI-SPEC's implementation map (§15) fits this structure directly.

The **results bleed-through has two causes**. (a) The `polish` harness scenario calls `goto(MENU)` and then builds a `ResultsScreen.new()` straight under `/root` while the live `MainMenu` is still the current scene (`playtest_driver.gd` lines 1990-2016, and the same for the practice results and FailScreen at 2032 and 2042). (b) `ResultsScreen` draws only a translucent dim, `Palette.alpha(BG, 0.85)`, so whatever sits behind it shows through. In a real dive that is the frozen board and HUD (`polish_09_results_first_record.png`); in the harness it is the menu (`polish_10_results_new_record.png`). The fix has to cover both: an opaque results backdrop, and harness scenarios that hide or free the current scene (or host the results in a real Gameplay) before overlaying.

Most of the data the visuals need already exists. Sources are `judged(lane, idx, judgment, error_s)`, the `HullScore` signals (combo, multiplier, streak, score, hull), `ChartData.tempo_map`, `Conductor.song_time()` and `Settings.low_effects`/`reduce_motion` with `settings_changed`. **The gaps:** `ChartData` has no `sections` and no time signatures, although `ParsedChart.events` and `ParsedChart.time_sigs` are parsed. **All 5 bundled charts contain `section` events and non-4/4 `TS` changes**, which contradicts the UI-SPEC note that bundled autocharts may have none. `SongEntry` has no sections, no album path and no intensity data. `ScoreStore.accuracy` is a hit-rate formula, not the D-08 weighted one, and records store no miss count or grade. The zip extractor drops `png`/`jpg`.

**Primary recommendation:** Build in the D-14 slice order, but start with a Wave 0 that (1) adds the colour-literal scan, contrast and layout keep-out test scaffolds, (2) adds a frame-time capture to the harness and measures the **current** build's baseline, and (3) fixes the results root cause, both the opaque backdrop and the harness hosting. Measure the perf gate **uncapped** (vsync off, `Engine.max_fps = 0`) during the capture window. A capped or vsync measurement cannot meet 4.35 ms p95 even on an empty scene on this machine (measured below).

- **D-04:** Stay in 2D (`_draw` + `Trench` projection) for the board. Use `canvas_item` shaders for glow/CRT/water shimmer, `GPUParticles2D` or `CPUParticles2D` (whichever is reliable in Compatibility) for snow/bursts, and `WorldEnvironment` glow if it works on Compatibility 2D (research verifies). - **D-07:** Menu music: a random bundled song's preview loops at -12 dB relative to music volume, with a Settings toggle "Menu music" (default on). It fades out over 400 ms when entering a dive.

- **D-11:** Album art: `album.png` / `album.jpg` in the song folder, loaded at runtime (Image.load), cached per song, max 512 px. Generated cover fallback, deterministic from the title hash.

- **D-13:** Transitions: a 300 ms "sonar wipe" (a radial ping expanding) between screens, skippable, and never blocking input.

### Results bleed-through: root cause (VIS-05)

1. **Harness hosting:** `sc_polish()` runs `await goto(MENU)` (line 1990), then `var rs := ResultsScreen.new(); get_tree().root.add_child(rs)` (2010-2011). The MainMenu stays the current scene, visible and focusable. The screenshot `polish_10_results_new_record.png` shows the "UNDERTOW" title and menu buttons behind the rows. The same pattern is used for the practice results (2032) and for `FailScreen` (2042). [VERIFIED: playtest_driver.gd + screenshot]
2. **Translucent results:** `ResultsScreen.setup()` adds `ColorRect` with `Palette.alpha(Palette.BG, 0.85)`. In a real dive the results are a child of `_run_root`, so the frozen board, HUD numbers and receptors show through at 15% (`polish_09_results_first_record.png`). [VERIFIED: results_screen.gd + screenshot]
3. **Input leak risk:** while hosted over the menu, the menu's buttons are still in the focus graph. ResultsScreen only links Retry↔Menu for up/down, so a stray left/right could reach menu buttons.

**Fix the planner must include (both halves):** the opaque results backdrop per UI-SPEC §8 (`AbyssBackdrop calm` at 100% plus `ABYSS_900` 55%), **and** harness changes. Before overlaying, set `cur().visible = false` and `cur().process_mode = PROCESS_MODE_DISABLED` (or `goto` an empty host scene, or run a real dive to DONE). The VIS-05 scene-tree test then asserts that no visible `MainMenu` exists. A pixel check samples the area behind the panels for menu-text luminance. Also give the new Results screen a closed focus loop over its 3 buttons (left/right/up/down all wrap inside).

### Pattern 1: Tokens and theme from one source
**What:** `Palette` holds every colour, size, spacing and duration. Build the Theme **in code** (`UiKit.build_theme()` returning a `Theme` from Palette tokens). Alternatively, keep `undertow_theme.tres` and add a test that its colours equal the Palette tokens.
**Why:** the `.tres` stores colours as float literals (`Color(0.039, 0.121, 0.039, 1)`), so it can silently drift from `palette.gd`. Every screen already calls `Palette.load_theme()`, so swapping its implementation is one change point.
**Migration aid:** keep alias constants (`ACCENT -> SONAR`, `TEXT -> TEXT_MID`, `REC_TEXT -> TEXT_HI`, `DESTRUCTIVE -> WARNING_RED`, `BG -> ABYSS_900`) until the last slice, then delete them. Retired-token usage today: 54 `Palette.ACCENT/TEXT/PANEL/DIM/BG/DESTRUCTIVE/REC_TEXT/dim()` references in `src/ui` plus about 15 in tests.

### Pattern 2: Effect nodes read settings at start and on change (copy Arena)
```gdscript
# Source: src/ui/arena.gd lines 125-134 (existing project pattern)
func _enter_tree() -> void:
	if not Settings.settings_changed.is_connected(_on_settings_changed):
		Settings.settings_changed.connect(_on_settings_changed)
func _exit_tree() -> void:
	if Settings.settings_changed.is_connected(_on_settings_changed):
		Settings.settings_changed.disconnect(_on_settings_changed)
```
For AV-05's "each new effect node reads the setting" test, give every effect node a common marker (e.g. `group "fx_settings_aware"` plus `func apply_effect_settings()`). The test can then enumerate the group in a running Gameplay/Menu, toggle `Settings.low_effects`, emit `settings_changed`, and assert each node's reported counts change.

### Pattern 3: Render-order split without z_index
The UI-SPEC order is Arena > HighwaySurface > FxLayer > Feedback > HighwayNotes > CockpitFrame > Hud > intro > overlays. **Use sibling order under `_run_root`, not `z_index`.** In Godot 4, `z_index` sorts across the whole CanvasLayer, so a high-z notes layer would also draw above the pause/results overlays that are appended later [ASSUMED: Godot z_index semantics from training; verify if z_index is considered]. Keep `Highway` as the state owner (tests read `g.highway._state`, `on_judged`, etc.) and give it a second drawing Control, `HighwayNotes`, which `Gameplay.start()` adds after FxLayer and Feedback and which draws by calling back into the Highway (`highway.draw_notes_into(ci)`). Put the board nodes (Arena, HighwaySurface, FxLayer, Feedback, HighwayNotes) under one `BoardRoot` Control so the Miss shake moves only the board. Today `Feedback.nudge_target = _run_root` moves the HUD too.

### Pattern 4: Pure, tested run statistics
```gdscript
# D-08 / UI-SPEC 4.13 (new pure class; do not change ScoreStore.accuracy semantics silently)
static func accuracy(p: int, g: int, m: int) -> float:   # -1.0 when nothing judged
	var n := p + g + m
	return -1.0 if n <= 0 else (p * 100.0 + g * 50.0) / float(n)
static func grade(acc: float, misses: int) -> String:
	if acc < 0.0: return "-"
	if acc >= 98.0 and misses == 0: return "S"
	if acc >= 93.0: return "A"
	if acc >= 85.0: return "B"
	if acc >= 75.0: return "C"
	return "D"
static func histogram(offsets_s: PackedFloat32Array) -> PackedInt32Array:  # 28 bins, -70..+70 ms
	var bins := PackedInt32Array(); bins.resize(28)
	for e in offsets_s:
		var i := clampi(int(floor((e * 1000.0 + 70.0) / 5.0)), 0, 27)
		bins[i] += 1
	return bins
```
Edge cases the tests must cover: exactly +70 ms goes to bin 27, -70 ms to bin 0, values beyond the range clamp to the end bins, and 98.0 with 1 miss gives A. Watch float rounding at bin edges: use `floor(x + 1e-9)` or work in integer microseconds.

### Pattern 5: Album art off the main thread, never during scans
Load on the same `WorkerThreadPool` + request-id pattern Song Select already uses for previews (`_preview_tasks`, `SongListModel.accept_result`). Build the `ImageTexture` on the main thread (call_deferred). Check `FileAccess.get_file_as_bytes` size first (cap at about 8 MB), then `Image.load_from_file`, reject absurd dimensions, crop and resize to ≤ 512. Use an LRU of 32. Generated cover: `title.strip_edges().to_lower().sha256_text()` bytes drive the gradient pair, arc corner and phase, which makes it deterministic and testable byte-for-byte.

### Pattern 6: Menu music and the Preview bus
Add a `Preview` bus to `default_bus_layout.tres` that sends to `Music` (so the music volume applies) and carries `AudioEffectSpectrumAnalyzer`. Alternatively create it at runtime with `AudioServer.add_bus` if editing the layout is undesirable. Use a `MenuMusic` autoload that survives scene changes (needed for the menu → song select cross-fade). It plays a random bundled song's preview at -12 dB, and `stop(fade_sec)` is called from `SongSelect._dive`, from `MainMenu` → Calibrate, and when Song Select's own preview starts. Bus volume today comes from `Settings.apply_audio()` for Master/Music/SFX only, which is fine because Preview sends into Music.

### Pattern 7: ScreenTransition as the single scene-change choke point
There are 6 `change_scene_to_file` call sites: `main_menu.gd:240`, `settings_screen.gd:597`, `song_select.gd:482`, `gameplay.gd:342`, `calibration_wizard.gd:434`, `drift_harness.gd:71` (debug, leave alone). The menu and settings already route through a `navigate` Callable seam for tests. Keep those seams *in front of* ScreenTransition so unit tests stay synchronous. Give ScreenTransition an `instant` flag that tests/harness can set, and run the Reduce-motion path. Swap the scene at full cover with `change_scene_to_file`; the reveal starts once the new scene is ready.

### Anti-Patterns to Avoid
- **Re-implementing chamfer panels per screen**: use `UiKit.style_panel()` (`StyleBoxFlat` with `corner_radius_top_left/bottom_right = CUT`, `corner_detail = 1`).
- **Per-frame allocation in `_draw`**: Highway already preallocates `PackedVector2Array`s (`_cable`, `_quad`, `_edge_l/_r`); keep doing this for strips, beat lines and gem polygons. Note that `NoteShape.draw` currently does `pts.duplicate()` + `append` per note per frame. NotePainter should cache unit polygons and transform them.
- **`Settings.bindings.display_name()` per frame**: Highway calls it for 4 labels every frame. Cache it on `settings_changed`.
- **A full-screen post shader over notes**: the CRT pass is a material on the surface polygon only (UI-SPEC §7.4 #2).
- **Touching `Conductor`/`InputJudge`/`HullScore`/`JudgeConfig`/`ClockModel`**: gate. Read `JudgeConfig.perfect_window`/`good_window` from a `JudgeConfig.new()` instance as Highway already does.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Particle bursts | Manual dot arrays with physics | `CPUParticles2D` pool (one-shot, fixed seed) | Deterministic screenshots, gravity/spread/scale curves built in |
| Spectrum bands | FFT on raw audio | `AudioEffectSpectrumAnalyzer` instance | Built in, thread-safe from the audio thread |

## Common Pitfalls

### Pitfall 1: Sections exist in charts but not in ChartData
**What goes wrong:** the banner never shows and the SPEC acceptance "screenshot at a section change" has no data.
**Why:** `ChartParser` stores `[Events]` into `ParsedChart.events`, but `ChartImporter.build` only extracts solos.
**How to avoid:** add `ChartImporter._sections(parsed, segs, res, delay)` that parses `text.begins_with("section ")` (and `prc_` for MIDI later), converts tick → sec with `_tick_to_sec` + delay, clamps to ≥ 0, sorts and dedups. Add a fixture test. Bundled charts (hrt 8, invisible 10, sea_shanty_2 6, space_synth_wave 10, synth_wave_april 6 `section` lines) can be used directly in harness screenshots. **The UI-SPEC's note that a fixture is needed is unnecessary.** [VERIFIED: grep of songs/*/notes.chart]

### Pitfall 2: Bar lines assume 4/4 but the bundled charts change meter
**What goes wrong:** bar lines drift off the music after a `TS 3`/`TS 2`/`TS 1`/`TS 8` change (invisible starts in 3/4; space_synth_wave has TS 1 and TS 2 passages).
**How to avoid:** carry `time_sigs` into ChartData (non-timing file; not in the fingerprint) and count beats-per-bar from it. The `.chart` `TS` denominator is `2^exp` (default exp 2 = quarter). Treat the beat as the quarter-note beat from the tempo map and the bar length as `num * 4 / 2^exp` quarter beats. If the planner keeps 4/4, record it as a known deviation for UAT. Recommendation: honour TS, since it is cheap.

### Pitfall 3: The theme `.tres` holds colour literals the scan won't see
The SPEC scan targets `src/ui/**/*.gd` and `scenes/**/*.tscn`, while `ui/undertow_theme.tres` is allowed. If the theme is hand-edited it can disagree with Palette. Build it from Palette in code, or add a theme-vs-palette equality test. Also scan for `Color.WHITE`-style named constants and `Color8(`, which the `Color("`/`Color(<number>` regex misses (allow `Color.TRANSPARENT`).

### Pitfall 4: Two different "accuracy" definitions
`ScoreStore.accuracy(p, g, m) = (p + g) / total * 100` (hit rate) is what Gameplay submits and what Song Select/menu show as "best accuracy". D-08 is weighted (`p*100 + g*50`). Stored records also have **no miss count**, so the Song Select "GRADE" best value (UI-SPEC §6) cannot be derived from existing records.
**Recommendation:** add the pure D-08 formula in a new class. From this phase on, submit the D-08 accuracy and store `best_grade` (and optionally `best_miss`) in ScoreStore, which is non-core. Show "-" for the grade on legacy records. Old saved accuracies are hit-rate values; accept the small inconsistency or show them only when re-earned. **Needs a planner decision** (see Open Questions).

### Pitfall 5: `variation_opentype = {"wght": 700}` silently does nothing
Measured on the real font: the `M` advance at 100 px is 86 at wght 400 and 90 at wght 700 with the **integer** tag `TextServerManager.get_primary_interface().name_to_tag("wght")` (= 2003265652). With the **string** key `"wght"` it is 84, i.e. the axis default (wght **200**, ExtraLight). The UI-SPEC writes `{"wght": 700}`; the executor must use the integer tag, or in a `.tres`, the integer key. The UI-SPEC's fallback test ("advance of M at 700 differs from 400") would catch it, so keep that test. [VERIFIED: 4.7.2 probe]

### Pitfall 6: The perf gate is unmeasurable as "p95 frame delta at the 240 Hz cap"
Measured on this PC in a scratch project (empty scene, `gl_compatibility`, opengl3):

| Mode | p50 | p95 | p99 |
|------|-----|-----|-----|
| vsync on (screen reported 59.94 Hz today) | 16.69 ms | 17.03 | 17.16 |
| vsync **off**, `Engine.max_fps = 240` | 4.17 ms | **4.55** | 4.71 |
| vsync off, uncapped (`max_fps = 0`) | 0.13 ms | **0.22** | 0.31 |

Even an empty scene fails 4.35 ms p95 under the 240 fps limiter (sleep jitter). It also depends on which monitor the window is on: earlier harness runs logged a 240 Hz screen and an RX 6600 XT, but today Godot sees one 59.94 Hz screen. **Recommendation:** for the 30 s capture window, set `DisplayServer.window_set_vsync_mode(VSYNC_DISABLED)` and `Engine.max_fps = 0`, record per-frame `Time.get_ticks_usec()` deltas from a priority-1000 node (like `frame_probe.gd`), compute p95 ≤ 4.35 ms (meaning the game *can* sustain ≥ 230 fps), and restore the previous vsync/max_fps afterwards. Also log `viewport_get_measured_render_time_cpu/gpu` p95 as diagnostics, plus the 240 Hz vsync average fps when the window is on a ≥ 240 Hz screen. This keeps the SPEC's intent (≥ 230 fps) but changes the measurement mode; **flag it to the user at UAT**. Measure the **current build first** (Wave 0) to know the headroom. [VERIFIED: scratch measurements]

### Pitfall 7: Menu music leaking into timing-critical audio
Calibration plays a click track and measures taps. If menu music is still playing (it persists in an autoload across scene changes), audio calibration is polluted. Stop it on entering Calibration and Gameplay, and at Song Select preview start. The harness should also turn `menu_music` off in `isolate_settings()` except in a dedicated menu-music scenario, so audio scenarios (a, c, drift, align) stay clean.

### Pitfall 8: Album art in exports and in zips
- Bundled songs live under `res://songs/...`. An `album.png` there would be **imported** (converted to `.ctex`), and the raw file is not in the export pack, so `Image.load_from_file("res://…/album.png")` fails in the exported build [CITED: class_image docs warn Image.load "may not work in exported projects"; ASSUMED for load_from_file on res://]. Bundled songs have no art today, so the generated cover is shown. If art is added later, load it via `ResourceLoader.exists()`/`load()` for `res://` paths.
- `ZipExtractor.ALLOWED_EXTS` = chart, ini, ogg, mp3, wav, opus, mid; **png/jpg are dropped**. Add `png`, `jpg`, `jpeg` with a per-file size cap. Existing extracted zip caches have an `ok` marker and won't re-extract. Bump an extractor version in the marker or accept that old zips show generated covers until a cache clear.
- The user's reference folder (`Desktop/Slipknot - Before I Forget`) has `album.png` (510 KB) but its chart is `notes.mid`, which is unsupported. It is good as an album-art **fixture source** but not as a playable song.

## Security Domain

`security_enforcement: true`, ASVS level 1. This phase is local UI; the relevant surface is **untrusted files read at runtime** (album images, zip contents, chart text).

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | n/a |
| V3 Session Management | no | n/a |
| V4 Access Control | no | n/a |
| V5 Input Validation | yes | Size cap before `Image.load_from_file`; dimension cap; decode failure → generated cover; section names via `SongIni.sanitize_text`-style cleanup and length cap (28 chars displayed); zip allow-list + per-file size limit for png/jpg |
| V6 Cryptography | no (sha256 used only as a deterministic hash for covers) | `String.sha256_text()` |
| V12 Files and Resources | yes | Never pass user files to `ResourceLoader`/`load()` (existing project rule for caches/scores); images only via `Image.load_from_file`; album lookup confined to the song's own folder (`chart_path.get_base_dir()`), no path traversal from ini fields |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Oversized/decompression-bomb image in a song folder or zip | Denial of service | File-size cap (≈8 MB), reject width/height > 4096 after load, load on worker thread, LRU cap 32 |
| Malformed PNG/JPG targeting the decoder | Tampering | Godot's built-in decoders only; failure is silent fallback; no custom parser |
| Hostile `section` text (huge/control chars) | Tampering / DoS | Existing parser `max_entries` cap; sanitize + truncate names for display |
| Zip path traversal for new image extensions | Tampering | Existing `ZipExtractor` path checks apply; only add extensions to the allow-list |
