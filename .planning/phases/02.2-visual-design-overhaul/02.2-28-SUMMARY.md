# Phase 02.2 Plan 28: Gamepad menus (G3 part 1) Summary

A on pad now confirms and B goes back on every Button-based screen. This works because `ui_accept` and `ui_cancel` in project.godot now include pad buttons A and B, and the keyboard defaults are kept. 25 new pad-only tests show that the main menu, the device prompt, song select, results, fail, pause, confirm dialogs, the intro and the unpaused dive all work with a controller alone.

## Root cause

The headless InputMap dump was right. Godot's built-in `ui_accept` only had Enter, KP Enter and Space, and `ui_cancel` only had Escape. Because of that, A and B did nothing on any `Button` screen. D-pad, left stick (`ui_up/down/left/right`) and Start (`pause`) were already mapped. Song select only worked because it reads pad buttons itself. Once the input map was fixed, the tests found one more real bug: the device-changed prompt.

## Screen -> broken -> fix

| Screen | What was broken | Fix |
|--------|-----------------|-----|
| Main menu | A did nothing (no joypad on ui_accept) | input map |
| Device-changed prompt | A did nothing; D-pad Down / Up moved focus to the menu items behind the prompt, so A could start an unexpected action | input map + `main_menu.gd`: Left/Right and Tab swap the two prompt buttons, and Up/Down stay put |
| Song select | Already worked (custom pad handler). Test confirms one A press = one dive, and that no Button inside can steal A | none (regression tests) |
| Results | A did nothing on the buttons; B did not go back (ui_cancel had no B) | input map |
| Fail screen | A did nothing | input map |
| Pause | A did nothing on the buttons; B did not resume | input map |
| Confirm dialogs | A did nothing; B did not cancel | input map |
| Goggles intro | Already worked (A = fire, Start = pause) | none (regression tests) |
| Unpaused dive | Already safe: no focused control, so A/B/D-pad do nothing; lanes LB/LT/RT/RB still reach LaneInput | none (regression tests) |

Proof of the RED state: with the old project.godot and main_menu.gd, 11 of the 17 menu tests failed. These were menu, prompt, results, fail, pause, dialogs, and focus after resume. The song select, intro and unpaused-dive tests passed both before and after, which is expected because they are regression guards.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Device-changed prompt leaked pad/arrow focus to the hidden menu**
- **Found during:** Task 2
- **Issue:** From Calibrate Sonar or Skip for now, Down/Up moved focus to the menu items behind the prompt. A then started that item, for example opening calibration from "Calibrate Sonar" in the menu.
- **Fix:** Explicit focus neighbours make the prompt modal for focus.
- **Files modified:** src/ui/main_menu.gd
- **Commit:** 9600c2f

**2. [Rule 3 - Blocking] Pad.flick sends through Input, not Viewport.push_input**
- Godot's Viewport moves focus on an InputEventJoypadMotion only when `Input.is_action_just_pressed` is also true. A bare `push_input` never updates Input state. Real controllers go through Input, so the game was never affected; only the test helper needed this. Documented in pad.gd.

Not changed (out of scope, plan 29): settings_screen, rebind_cell, step_slider, calibration_wizard. The fail screen has no B -> Back to Menu, because the plan does not require it and Esc behaviour there stays as it was.

## Remaining for the user's PC
