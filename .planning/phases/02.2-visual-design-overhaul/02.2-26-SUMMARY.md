# Phase 02.2 Plan 26: G1 judge-window sync proof and widening Summary

Gap G1 ("I'm missing notes that I should be hitting, visually") is now addressed in two ways. Tests show the board draws each gem exactly where the judge places the note: gem centre equals receptor centre equals hit line within 0.5 px in all 60 cases. They found one 2 px offset on the triangle gem, which is now fixed. The judge windows are also wider: Perfect ±50, Good ±100, early-miss 130 ms. That change is in `judge_config.gd` only, and the timing gate was re-baselined to the new commit.

## What was done

### Task 1: sync proof (TDD)
- RED `c33044a`: `tests/test_visual_sync.gd` covers behaviours A-F. It needed seams that did not exist yet, and Test D failed on the triangle.
- GREEN `d8b50d9`:
  - `Highway.gem_depth(i)` / `gem_center(i)` / `receptor_center(lane)` were added. `draw_notes_into`, `draw_halos_into`, `_draw_receptors` and `_draw_lane_numbers` now call these functions, so the drawing code and the tests cannot drift apart.
  - `NotePainter.unit_shape` recentres every kind on its bounding box before clipping the top-light. The specular moves by the same shift. The pad ring is built from the same polygon, so gem and pad stay identical.

**Sync findings (what was off, and by how much):**

| Candidate cause | Result |
|---|---|
| Gem centre vs receptor centre vs hit line, 4 lanes x 5 speeds (0.5-3x) x 3 visual offsets (-0.1/0/+0.05) | No mismatch. Delta 0.0 px in all 60 cases (both use `Trench.point(lane_f, 0)`). |
| Visual-offset sign | Matches. Highway `_vt = _st + Settings.visual_offset` and the calibration wizard `vt = st + pending_visual` use the same sign. +0.05 makes the gem reach the line 50 ms early. |
| Process order / stale clock | OK. Conductor `process_priority` -1000 < Highway/HighwayNotes 0. `_st == conductor.song_time()` exactly and `_vt == _st + visual_offset`. No smoothing. |
| Gem visual centre vs anchor | **Mismatch, fixed.** The triangle unit polygon spans y -1..+0.9, so its bbox centre was at y -0.05 r. At the hit line (r = 41 px) the triangle gem and its pad were drawn **2.05 px above** the line. At 1x that is about **2.1 ms** early-looking; at 3x about 0.7 ms. Diamond, circle and square were already centred. |
| Past-the-line motion | OK. Pending gems keep moving below the line (d 0..-0.06 checked). Only missed remnants are pinned at d = -0.06. |

So the drawing was not the main cause of G1. The ±35 ms Perfect window was simply narrower than what a gem visually "on the receptor" looks like:

**Pixels per window at the hit line** (gem speed at the line = TRAVEL x (1 + PERSPECTIVE) / approach = 0.997 px/ms at 1x, 2.99 px/ms at 3x, 0.498 px/ms at 0.5x; gem radius at d = 0 is 41 px):

| Speed | Old Perfect ±35 ms (early / late px) | New Perfect ±50 ms | New Good ±100 ms |
|---|---|---|---|
| 0.5x | 17 / 18 | 24 / 26 | 47 / 53 |
| 1x | 34 / 36 | 47 / 53 | 89 / 113 |
| 3x | 93 / 120 | 127 / 182 | 220 / 307 (late end clamped at D_MIN) |

At 1x a gem still visibly overlaps its 41 px receptor up to about ±41 ms. Under the old windows, the last 6 ms of that overlap scored Good, not Perfect. With the new Perfect (±47-53 px) the Perfect window now covers the whole visible overlap.

**Min same-lane gap per bundled song** (informational; the judge was not changed). The judge scores a press against the lane's queue head. When a lane gap is under 2 x Good (200 ms), a press meant for the next note can be scored against an earlier note that is still pending, but only if that earlier note was not hit.
