# Phase 2.2 Plan 01: Wave 0 guardrails (timing gate, perf baseline, results bleed-through) Summary

This plan adds three guardrails. A one-command timing-core gate. An uncapped 1920x1080 frame-time capture that recorded the pre-phase baseline: Full p95 1.03 ms and Low p95 0.83 ms, against a gate of 4.35 ms. The third is the D-20 results fix: the results backdrop is now opaque, the harness hides the current scene before showing an overlay, and tests check that no menu shows behind the results.

## What was built

**Task 1 (991d910): timing gate, perf and visual scenarios, baseline**
- `tools/check_timing_gate.ps1` runs `git diff --stat 72e21ce` and `git status --porcelain` on conductor / clock_model / input_judge / judge_config / hull_score. It prints `TIMING GATE OK` (exit 0) or the diff plus `TIMING GATE FAILED` (exit 1). Both paths were checked by appending a line to judge_config.gd and then reverting it.
- `sc_perf` works in four steps:
  - It finds the densest 30 s Expert window across the 5 bundled songs (chart parse only, no audio decode), using windows that start within the first 60 s.
  - It forces a 1920x1080 render and checks that the window is 1920x1080 and not exclusive fullscreen.
  - It runs an autoplay dive and waits for the window start. `capture_frames(30)` turns vsync off and sets `Engine.max_fps = 0`, records per-frame deltas from a priority-1000 node plus the render CPU/GPU time, then restores vsync and max_fps.
  - It restarts the run with Low effects and captures the same window. Refresh rate is logged only. A 5 s vsync-on average fps is also recorded when the screen is at least 239 Hz.
- `sc_visual` runs one autoplay dive on a bundled song and saves the `visual_baseline` screenshot.
- Driver timeouts are `perf` 470 s and `visual` 420 s. In run_all, both are in the default list before drift, with limits of 480 s and 450 s.
- In `02.2-PERF.md`, the baseline row is sea_shanty_2 starting at 0.07 s, 122 notes, wait method, 1920x1080, 59.94 Hz, RX 6600 XT:

  | Effects | p50 | p95 | p99 |
  |---------|-----|-----|-----|
  | Full | 0.848 ms | 1.030 ms | 1.122 ms |
  | Low | 0.666 ms | 0.828 ms | 0.912 ms |

  Render CPU p95 is 0.124 ms and GPU p95 is 0.388 ms.

A stricter check also confirms the backdrop is uniform there.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's way of forcing the capture window locked frames at 60 fps**
- **Found during:** Task 1
- **Issue:** The plan said to use a borderless window sized to the screen at 0,0 when the screen is 1920x1080. Godot reported that window as `WINDOW_MODE_EXCLUSIVE_FULLSCREEN` (mode 4), and there vsync could not be turned off: every frame took 16.7 ms and p95 was 17.0 ms. Scratch probes ruled out other causes (render-time measurement, the launch method, the fullscreen-to-windowed order).
- **Fix:** On a 1920x1080 screen, use the game's own default `WINDOW_MODE_FULLSCREEN` (borderless, D-06), which renders at 1920x1080 with vsync off. Other screens get a windowed 1920x1080. A new check, "capture window is not exclusive fullscreen", guards against a regression.
- **Files:** tools/playtest/playtest_driver.gd. **Commit:** 991d910

**2. [Rule 2] Stricter bleed-through pixel check**
- The < 0.35 luma rule alone would also pass the old 0.85 dim (menu text dimmed to about 0.1). I added "results backdrop uniform where the menu text was (max luma <= backdrop + 0.02)" so the check actually catches bleed-through. **Commit:** 08561c3

**Other notes**
- The `perf` window search uses `wait`. Gameplay has no start-position option and Conductor (timing core) has no public seek.
- `run_all.ps1 -Scenarios perf,visual` via `-File` passes the list as one string. The scenarios were run through `powershell -Command "& ./tools/playtest/run_all.ps1 -Scenarios visual,perf"`.
