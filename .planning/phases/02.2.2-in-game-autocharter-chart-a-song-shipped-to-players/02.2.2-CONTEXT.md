**Gathered:** 2026-10-14 (orchestrator; user request 2026-10-13: "an autocharter inside the game, so it can be shipped with the game, so anyone can transform any songs to be playable"). No discuss session yet; the delivery-model question was asked but interrupted by an app restart, so D-03 is the recommended default and is open to the user's override.
**Status:** Ready for research

<domain>
## Phase Boundary

Today the Phase 02.1 autochart pipeline (tools/autochart, Python: htdemucs stems, beat_this tempo map, D3 onsets,
Basic Pitch contour lanes, Expert->Hard/Medium/Easy reductions, sync gate) runs only on the dev PC and "never
ships" (tools/autochart/README.txt). This phase makes it usable by any player from inside the game.

</domain>

<decisions>
## Implementation Decisions

- **D-01 In-game flow:** a "Chart a song" entry (main menu and/or Song Select) lets a player pick an audio file
  they own (mp3/ogg/wav/flac), choose the charted instrument (auto-ranked default, as stem_rank.py does) or the
  "instrument lanes" mode (STEM-04), see progress with cancel, and get a new library entry (song folder with
  notes.chart + song.ini + audio) that plays like any other song. Failures show a clear reason.
- **D-02 Same proven pipeline:** charts come from an extracted instrument stem, never the full mix (CONT-02 stays
  rejected). Reuse the Phase 02.1 stages and decisions (soundfile decode, not demucs' own MP3 decode; beat phase
  correction; D3 onsets; octave rules; reductions; preview pick). Sync quality must match the bundled songs.
- **D-03 Delivery (default, user may override):** optional "Autocharter pack" downloaded on first use. The base
  game zip stays small. The pack contains a self-contained runtime (e.g. embeddable/uv-managed CPython + pinned
  wheels from requirements-a/b.txt + the htdemucs, beat_this and basic-pitch model weights) so players need no
  Python install. Researcher compares: (a) packaged Python runtime pack, (b) ONNX models via a Godot GDExtension,
  (c) bundling in the base zip — sizes, CPU time per song, risk — and recommends; the planner implements the
  chosen option. If research finds (a) impractical, report before planning.
- **D-04 Where the pack comes from:** a GitHub Release asset on the user's repo (ccxmxrgo/undertow), downloaded
  over HTTPS with a pinned SHA-256 checked before unpacking into user:// (or %APPDATA%\...\UNDERTOW). Never run
  anything that fails the hash. Zip-slip safe extraction.
- **D-05 Process isolation:** the game launches the pipeline as a child process (OS.create_process /
  OS.execute_with_pipe) with explicit argument lists (no shell strings), reads progress from stdout/JSON, can
  cancel it, and never blocks the main thread. Untrusted audio paths are passed as arguments, never interpolated.
- **D-06 Output:** charts are written to the player's Songs folder (user://songs/<slug>/) with song.ini
  (`charter = UNDERTOW autochart`), then the library rescans. Bundled songs are unaffected.
- **D-07 Timing core untouched;** timing gate must print TIMING GATE OK. Sync of generated charts is tested
  against the existing note_sync gate on at least one CC0 song (Pro Sensory tracks are CC0).
- **D-08 No copyrighted audio in the repo or the pack.**
- **D-09 Friend build:** ends with a friend zip (next version after v0.5.3) plus the published pack release; README
  "WHAT'S NEW" explains Chart a song and the one-time download size. Publishing a GitHub Release is an
  outward action: prepare the asset and command, and ask the user before publishing.

### Claude's Discretion

</decisions>
