# Phase 02.2.2: Code Review Report

**Reviewed:** 2026-10-15T02:22:42Z
**Depth:** deep
**Files Reviewed:** 30

## Summary

Scope: `git diff 73bc762~1 HEAD -- src tests tools scenes`, with build outputs and `.planning` left out. The review
read the code against the CONTEXT decisions (D-04, D-05, D-12, D-13) and the threat registers of plans 01 to 10.

The main design holds up. Pins are compiled in (no downloaded manifest), the URL must be https, parts get a size
and SHA-256 check before extraction, zip-slip names are refused in two passes, the argv is a fixed token list,
free text goes only into job.json, the stdin-EOF watchdog is in place, and every delete is checked against the
pack root. The runner, the protocol parser and the job.json validation on both sides are careful.

Where it falls short:

- **The hash check and the extraction read the zip separately (CR-01).** For "Install from Folder" this lets a
  hostile file source pass the pinned-hash gate.
- **The extracted tree is never checked after it is written.** Write errors are ignored (WR-03). A partial update
  replaces a whole root while only part of its content was re-extracted (WR-06). Both can leave a pack marked
  installed over damaged files.
- **Path checks compare strings only (WR-04, WR-05).** The root guard follows Windows junctions. Comparisons are
  case-sensitive, but the Python side calls `resolve()` on its paths.
- **Some cancel and finish ordering is wrong in the state machine (WR-01, WR-09, WR-10).**

Items marked **[pack rebuild]** change files in `tools/autochart` that ship in the app part. Fixing them changes
the pinned hash, so each one requires `build_pack.ps1 -AppOnly` and regenerating `pack_spec.gd`. The pack is not
published yet, so this is still possible without a new tag.

## Critical Issues

### CR-01: The pinned hash is checked on one read and extraction uses another (TOCTOU, defeats D-04 for Install from Folder)

**File:** `src/autocharter/pack_installer.gd:214-220, 264-269, 340-359, 362-384` (plus `pack_extractor.gd:28-82`)
**Issue:** `_verify_task` opens the part, hashes it and closes it. Later, `_extract_task` re-opens the same path
twice: `ZipExtractor._central_sizes` and then `ZIPReader.open`/`read_file`. Nothing ties the bytes that were hashed
to the bytes that get extracted.

With "Install from Folder", `source_dir` is any folder the player picks, and the files are read in place. That
folder can be a network share, a USB stick or a folder a friend shared. A hostile SMB server, or any writer racing
the installer, can return the genuine bytes while the hash is computed and different bytes during extraction.
Those bytes end up in `v1/app/*.py` and `v1/rt/`, the marker records the good pins, and the game then runs
`python.exe` on them. This bypasses the only control in front of downloaded code (D-04). It also contradicts
T-02.2.2-42 ("every part is still size/hash-checked").

The same gap exists for `dl/`. There it only matters to a same-user attacker, so it is lower risk.

**Fix:** Pin the bytes before they are used. Copy every `source_dir` part into `dl/` first, then hash the copy. The
`_reused` / `in_dl` handling already supports this. While a part is being verified and extracted, keep it open
with exclusive access, or re-hash it inside the extraction task immediately before `ZIPReader.open` and fail when
the size or modified time changed:
```gdscript
# _next_part(), source_dir branch: copy into dl/ first, then verify the copy
var dest := AutochartPaths.dl_dir().path_join(pname)
DirAccess.make_dir_recursive_absolute(dest.get_base_dir())
if DirAccess.copy_absolute(src, dest) != OK:
    _fail("not_available", "Part %s could not be read from the chosen folder." % pname)
    return
_reused = false
_begin_verify(dest)   # extraction later reads only files under dl/
```

## Warnings

### WR-01: A cancel that races the end of the job reports "Charting stopped" although the song was installed

**File:** `src/autocharter/autochart_runner.gd:64-68, 160-166`; `src/ui/chart_song_screen.gd:1159-1176`; `tools/autochart/autochart.py:688-697`
**Issue:**
1. Cancel stays enabled through the `install` stage. `install_atomic` can finish moving the folder into
   `songs_root`, and then the kill lands before `done` is printed.
2. `cancel()` sets `_cancelled = true` even when the process has already exited with code 0 and a `done` event is
   buffered. `_finish` checks `_cancelled` before `_done_ev`, so the run counts as cancelled.

In both cases the screen says "Charting stopped." The confirm dialog promised "The chart for X will not be
saved", yet the song shows up after the next rescan. A retry then creates `slug_2`, a duplicate.
**Fix:** In `_finish`, let a received `done` event (or exit 0) win over `_cancelled`:
`if _cancelled and _done_ev.is_empty(): cancelled.emit(); return`. In `_on_runner_stage`, disable
`cancel_job_button` once the stage is `install`. In `cancel()`, only set `_cancelled` when `adapter.is_running()`.

### WR-02: `_verify_task` can spin forever on a read error or short read

**File:** `src/autocharter/pack_installer.gd:351-355`
**Issue:** The loop `while f.get_position() < f.get_length(): ctx.update(f.get_buffer(HASH_CHUNK))` never moves
forward when `get_buffer` returns an empty buffer. That happens on an I/O error, an unplugged USB stick or a
dropped network share (the case Install from Folder invites), while `get_length` keeps reporting the old size. The
worker then busy-loops and the UI stays on "Checking part N / M" until the player cancels.
**Fix:**
```gdscript
var buf := f.get_buffer(HASH_CHUNK)
if buf.is_empty() or f.get_error() not in [OK, ERR_FILE_EOF]:
    result = "mismatch"
    break
ctx.update(buf)
```

### WR-03: Extraction ignores write failures, so `installed.json` can sit over truncated files

**File:** `src/autocharter/pack_extractor.gd:78-84`; `src/autocharter/pack_installer.gd:387-441`
**Issue:** The return value of `f.store_buffer(...)` (a bool in Godot 4.4 and later) and `f.get_error()` are never
checked. The free-space check is only a hint: `free == 0` means "unknown, continue", and partial updates skip it
entirely. If the disk fills or antivirus blocks a write, files come out truncated or empty. The extraction still
reports `ok`, finalize writes the marker with every pin, and `is_installed()` returns true. Integrity was only
proven for the zip, never for the tree on disk. The selftest is the only remaining guard.
**Fix:** Treat a failed write as fatal:
```gdscript
var data := zr.read_file(p[0])
if not f.store_buffer(data) or f.get_error() != OK:
    f.close(); zr.close()
    return {"ok": false, "error": "write_failed", "written": written}
```
Optionally compare the bytes written with the central-directory size for each entry.

### WR-04: The recursive-delete root guard compares strings only and follows junctions and symlinks

**File:** `src/autocharter/pack_installer.gd:556-569`; `src/autocharter/work_cache.gd:183-196`; `src/autocharter/pack_paths.gd:69-72`
**Issue:** `is_under_root` checks a string prefix after `simplify_path()`. `_rm_tree` then recurses into every entry
returned by `DirAccess.get_directories_at`. On Windows that list includes directory junctions and symlinks
(FILE_ATTRIBUTE_DIRECTORY | REPARSE_POINT). The function deletes every file inside the link target and only then
removes the link itself.

So a junction anywhere under `%LOCALAPPDATA%\UNDERTOW\ac` makes "Remove Autocharter Pack", "Clear Chart Cache",
prune, or an install cleanup delete data outside the pack root. T-02.2.2-46 claims deletes are confined to the
root, and this breaks that claim. The junction could be planted, or be a user's space-saving link. The bug exists
in two copies of `_rm_tree`, so both must be fixed.
**Fix:** Do not descend into links. Remove the link itself:
```gdscript
var da := DirAccess.open(p)
for d in DirAccess.get_directories_at(p):
    var child := p.path_join(d)
    if da != null and da.is_link(child):
        DirAccess.remove_absolute(child)   # removes the junction, not its target
        continue
    _rm_tree(child)
```
Keep one shared implementation (see IN-08).

### WR-05: Godot compares paths case-sensitively against paths the Python side resolved

**File:** `src/autocharter/work_cache.gd:51,58,87`; `src/autocharter/pack_paths.gd:69-72`; `src/ui/chart_song_screen.gd:1138,1162,1272`; `tools/autochart/stages/job.py:81,272-276`
**Issue:** `load_job` calls `Path.resolve()` on `work_root` and `songs_root`, so the `work.dir` and `done.folder`
events carry the canonical path: real casing, 8.3 names expanded, junctions and `subst` drives resolved. Godot
builds its own paths from `LOCALAPPDATA` and `user://` and compares them byte for byte. When the two differ, for
example a profile folder whose on-disk casing differs from the env var or a redirected AppData:
- `remove_unfinished` returns false and the unfinished stems stay on disk;
- prune's `protect` never matches;
- `last_song_id` does not match the scanned song id, so Play Now opens Song Select on another song.

None of this is dangerous because it fails closed, but each feature fails without any message.
**Fix:** Compare paths case-insensitively on Windows (`to_lower()` on both sides inside `is_under_root` and
prune). Better, stop trusting child-reported paths: Godot can compute the work dir itself, and the folder can be
derived from `songs_dir().path_join(slug)` after checking `slug` against `^[a-z0-9_]{1,48}(_\d{1,2})?$`.

### WR-06: A partial update replaces a whole root even when several parts share it

**File:** `src/autocharter/pack_installer.gd:110-123, 314-321, 406-421`; `tools/autochart/pack_build.py:227-239`
**Issue:** `parts_to_fetch` puts only the changed parts into `_todo`, and only those are extracted into staging.
`_finalize_task` then deletes `vdir/<root>` and renames `staging/<root>` in its place. When two parts share a root,
the unchanged part's files are lost but the marker still records its pin. `pack_build.split_groups` produces
exactly this case on its own: any part with more than 55000 entries becomes `-a` and `-b` with the same roots. The
result is a broken pack that `is_installed()` reports as complete. The bug is latent today because app, NOTICES
and models each have one part.
**Fix:** In `parts_to_fetch`, when a changed part has a root that another part also uses, add every part that uses
that root to the fetch list (or fall back to a full install). Alternatively, extract the unchanged parts again from
`dl/` before the swap.

### WR-07: No retry when renaming the staging folder fails, so one antivirus lock fails the whole install

**File:** `src/autocharter/pack_installer.gd:404-405, 419-421`
**Issue:** `DirAccess.rename_absolute(staging, vdir)` (MoveFileEx on a tree of about 940 MB) often fails briefly
with ERROR_ACCESS_DENIED or SHARING_VIOLATION while Defender scans freshly written DLLs and exes. The finding
covers both renames, `staging` to `vdir` and the per-root renames. One failure goes to `_fail` and `_cleanup_run`,
which deletes staging, so the player waits through a full re-extraction. The UI note even says antivirus scans
can slow setup down.
**Fix:** Retry the rename a few times with backoff on the worker thread, checking the cancel flag between tries,
for example 10 attempts at 500 ms, before reporting `rename_failed`.

### WR-08: The dev-only `bp_python` key in job.json makes the job run any executable [pack rebuild]

**File:** `tools/autochart/autochart.py:576-583` (`_bp_mode`); `tools/autochart/stages/pitch_bp.py:120-124`
**Issue:** If `job.json` contains `bp_python`, the job switches to worker mode and `subprocess.Popen`s that path.
The plan 05 threat model treats job.json as "untrusted on disk (T-02.2.2-18)", and this one key turns a
modified job.json into arbitrary process execution. That path does not cross a privilege boundary today. It is
still a dev hook in the shipped code path, and the game never writes the key.
**Fix:** In pack mode (`_pack_version_dir() is not None`), refuse `bp_python`. Allow it only when an explicit dev
flag is passed on the command line, never through job.json. Then rebuild with `-AppOnly` and regenerate
`pack_spec.gd`.

### WR-09: Confirm dialogs stay open after the run ends; the stale "Stop Test" button then sends the player to the menu

**File:** `src/ui/chart_song_screen.gd:896-912, 1133-1155, 1167-1176`
**Issue:** `_on_installed` and `_on_failed` close the dialog. `_on_runner_finished` and `_on_runner_failed` do not.
If the job or selftest ends while "STOP CHARTING?" or "STOP THE TEST?" is open, the screen switches to the result,
pick or error state underneath the dialog.
- Confirming "Stop Test" then calls `_go(MENU_SCENE)` and throws away a selftest that passed.
- "Keep ..." tries to focus a hidden Cancel button, so a gamepad player is left with nothing focused.
- `drop_files` and Esc stay blocked while the stale dialog is open.

**Fix:** Call `_close_dialog()` at the start of `_end_run()`. In each confirm callback, check that the state is
still the one the dialog was opened for, for example `if _run_mode != "selftest": return`.

### WR-10: A pending Play Now scan can switch scenes after the player has moved on

**File:** `src/ui/chart_song_screen.gd:1240-1273, 1276-1288`
**Issue:** While `_adding` is true, "Chart Another Instrument" and "Back to Menu" still work. If the player
presses "Chart Another Instrument" during the rescan, `_on_play_scan_finished` fires later. It calls
`_open_new_song()` and jumps to Song Select from the options state, or from the running state if the player has
already started a new job. Leaving the screen kills that job.
**Fix:** Disable the other result buttons while `_adding` is set. In `_on_prior_scan_finished` and
`_on_play_scan_finished`, return unless `_state == "result" and _adding`. Clear `_adding` in `_restore_options`.

### WR-11: Remove Autocharter Pack leaves the stem cache behind, and the player cannot clear it afterwards

**File:** `src/autocharter/pack_installer.gd:176-185`; `src/ui/chart_song_screen.gd:924-935`
**Issue:** `remove_pack` deletes `v1/`, `staging_v1/` and `dl/`. It keeps `work/`, which holds up to 3 songs of
float32 decoded audio plus 4 stems each (hundreds of MB per song), and `cache/numba`. The dialog says "This frees
about 1 GB". After removal the screen shows `pack_missing`, and "Clear Chart Cache" is only reachable from `pick`,
which needs an installed pack. The remaining data can only be deleted by reinstalling the 400 MB pack or by
deleting it by hand.
**Fix:** After a successful removal, also call `AutochartWorkCache.clear(AutochartPaths.work_root())` and remove
`root()/cache`. Alternatively, offer Clear Chart Cache in `pack_missing` when `work/` exists.

## Info

### IN-01: The installed marker is written non-atomically

**File:** `src/autocharter/pack_installer.gd:188-196, 435-440`
**Issue:** A crash or power loss while `installed.json` is being written leaves an unparsable marker.
`_read_marker` then returns `{}`, which forces a full 400 MB re-download.
**Fix:** Write `installed.json.tmp`, then `DirAccess.rename_absolute` it over the marker.

### IN-02: The 2 GiB free-space requirement is too small for a reinstall over an existing pack

**File:** `src/autocharter/pack_installer.gd:24, 149-157`
**Issue:** Peak use during a full reinstall is the `dl/` zips (about 400 MB) plus staging (about 940 MB) plus the
old `vdir` (about 940 MB), roughly 2.3 GB. Partial updates skip the check entirely.
**Fix:** Require `download_bytes + unpacked_bytes * 2` (or subtract the size of the existing `vdir`). Check partial
updates too.

### IN-03: A killed install in the cross-volume path leaves junk folders in Songs [pack rebuild]

**File:** `tools/autochart/stages/job.py:229-264`
**Issue:** A kill between the steps of `_install_copy` leaves `songs_root/.tmp_<slug>` behind, or `<slug>` without
`notes.chart`. The next run then picks `<slug>_2`. Neither folder is ever cleaned up.
**Fix:** At the start of `install_atomic`, sweep stale `.tmp_*` folders, and folders without `notes.chart` whose
name matches the slug pattern.

### IN-04: Non-ASCII song names all become the folder `song`, `song_2`, ... [pack rebuild]

**File:** `tools/autochart/autochart.py:389-392`
**Issue:** `slugify` keeps only `[a-z0-9]`, so Japanese or Cyrillic titles collapse to `song`. After 99 of them the
job fails with "A song with this name already exists."
**Fix:** Fall back to `song_<first 8 hex of the source SHA>` when the slug is empty.

### IN-05: The Godot and Python job validators disagree on number types

**File:** `src/autocharter/job_protocol.gd:286, 309-313` vs `tools/autochart/stages/job.py:103-105, 128-130`
**Issue:** Godot accepts `version`/`threads` as floats and truncates them with `int()`. Python requires real ints.
`make_job` always produces ints, so this does not happen today, but the two "validate" functions do not match.
**Fix:** In `validate`, require `job["version"] is int` and `job["threads"] is int`.

### IN-06: `release_pack.ps1` hardcodes a personal path

**File:** `tools/autochart/release_pack.ps1:23`
**Issue:** The default `-ArchiveRoot "C:\Users\User\UNDERTOW-release-archive"` contains the developer's profile
path.
**Fix:** Default to `Join-Path (Split-Path -Parent $root) "UNDERTOW-release-archive"`.

### IN-07: Worker mode leaves a short window for an orphaned Basic Pitch process (not shipped) [pack rebuild]

**File:** `tools/autochart/stages/pitch_bp.py:120-127`
**Issue:** `Popen` starts the worker before `AssignProcessToJobObject`. A kill in that gap leaves the worker
running. The code is unused while the pack is a single merged interpreter.
**Fix:** Create the worker suspended (`CREATE_SUSPENDED`), assign it to the job, then resume it, or launch it
through a job-wrapped launcher.

### IN-08: `_abs` and `_rm_tree` are duplicated in four places

**File:** `src/autocharter/pack_paths.gd:13-15`, `pack_extractor.gd:15-17`, `pack_installer.gd:540-569`, `work_cache.gd:135-196`
**Issue:** The safety-critical delete helper has two copies, and path normalisation has four. WR-04 and WR-05 must
each be fixed in every copy.
**Fix:** Move `norm()` and a link-safe `rm_tree()` into `AutochartPaths` and call them from everywhere.

### IN-09: The `replace=True` install path is unreachable from the game and can lose a song if killed

**File:** `tools/autochart/stages/job.py:280-303`
**Issue:** The game never sets `replace`. If it ever does, a kill or watchdog exit between `_move_dir(dest, old)`
and `_move_dir(out_dir, dest)` leaves the player's song in `work/.../old_<slug>`, where prune later deletes it.
**Fix:** Before exposing `replace`, keep `old_` inside `songs_root` as a dot folder and restore it at the next job
start, or rename it instead of moving it.
