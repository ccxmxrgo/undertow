### Locked Decisions

  rejected). Reuse the Phase 02.1 stages and decisions (soundfile decode, not demucs' own MP3 decode; beat phase
  correction; D3 onsets; octave rules; reductions; preview pick). Sync quality must match the bundled songs.
- **D-03 Delivery (default, user may override):** optional "Autocharter pack" downloaded on first use. The base
  game zip stays small. The pack contains a self-contained runtime (e.g. embeddable/uv-managed CPython + pinned

- **D-04 Where the pack comes from:** a GitHub Release asset on the user's repo (ccxmxrgo/undertow), downloaded

- **D-09 Friend build:** ends with a friend zip (next version after v0.5.3) plus the published pack release; README

## Summary

Option (a), a downloadable Python runtime pack, is practical. It is the clear recommendation. I measured the published artifacts. One CPython 3.12.15 (python-build-standalone "install_only_stripped", 22.0 MB), the venv-A pins plus the Basic Pitch set, and the two model files come to **about 410 MB compressed (±10%) and about 0.95 GB on disk**. Python writes about 0.1 GB of bytecode on first run, on top of that. torch is the largest single piece: the CPU wheel is 114.5 MB compressed and 427 MB unpacked, and 92 MB of that (headers, `.lib` import libraries) can be pruned. The model files are 84.0 MB (htdemucs) and 81.1 MB (beat_this final0). Both hashes match README.txt, and they deflate by only 7%. For comparison, the current base friend zip is 65 MB. So the pack stays optional, as D-03 says. Bundling in the base zip (option c) would make the zip about 7x bigger for every friend, including those who never chart a song.

The two interpreters can very likely be merged into one, and that saves about 100 MB compressed and 0.3 GB on disk. basic-pitch 0.4.0 picks its backend at **import time**: it tries `import tensorflow`, then coremltools, then tflite, then `onnxruntime` (read from the 0.4.0 wheel's `__init__.py`). The Python-version marker that pulls tensorflow on 3.11+ applies only at install time. Install it in the 3.12 runtime with `--no-deps`, add `onnxruntime==1.23.2` (a cp312 wheel exists) and its small pure-Python dependencies, and it will load `nmp.onnx`. A Wave 0 spike must confirm that Basic Pitch output on the bundled songs' stems equals the venv-B output. librosa 1.0 vs 0.11 and numpy 2.5 vs 2.2 could change the resampling. If it does not match, fall back to shipping both interpreters (about 520 MB / 1.3 GB).

Option (b), ONNX models through a Godot GDExtension, would be smaller (about 180 MB), but it is a rewrite. I found no maintained onnxruntime GDExtension for Godot 4.x. htdemucs only exports to ONNX with the STFT/iSTFT moved outside the graph. beat_this ONNX exports exist from the community, but the log-mel front end stays outside the graph. Every numpy/scipy/librosa stage would have to be ported to C++: decode, demucs segmenting and overlap-add, the beat repair and phase correction, the D3 onsets, the Basic Pitch note post-processing, the librosa sections and soxr. That is weeks of work and puts the measured sync quality at risk. Rejected for this phase.

On the Godot side (read from the 4.7-stable source):
- `OS.execute_with_pipe` creates the child with `CREATE_NO_WINDOW`, so no console window flashes.
- On Windows, `get_length()` on the returned pipe is `PeekNamedPipe`, so you can poll it every frame without blocking.
- `OS.kill` is `TerminateProcess` on that one PID, so the pipeline must not spawn grandchildren.
- Arguments are quoted, but embedded quotes are not escaped, so free text must never be put on argv.
- `HTTPRequest` follows GitHub's cross-host redirect (`max_redirects` 8). It deletes a partial `download_file` on failure, so there is no resume. Use several independently hashed part zips instead of one big file.
- `ZIPReader` reads whole entries into memory and has no size query. The project's `ZipExtractor` already has the central-directory pre-scan and `safe_rel` to reuse.

**Primary recommendation:** Ship a "pack v1" as 4 GitHub Release zip parts, each with its SHA-256 pinned in GDScript:
- app: the pipeline code, about 0.2 MB
- rt-core: CPython plus the scientific stack, about 160 MB
- rt-torch: about 97 MB
- models: about 153 MB

The game downloads, verifies and extracts them into `%LOCALAPPDATA%\UNDERTOW\ac\v1`. It then runs one new entry point, `python -I -X utf8 -u app/autochart.py job <job.json>`, through `OS.execute_with_pipe`. Progress comes back as ASCII JSON lines on stdout. Separation and Basic Pitch run in-process, so `OS.kill` cancels everything.

Why LOCALAPPDATA: user:// is `%APPDATA%\Godot\app_userdata\UNDERTOW`, which is the **Roaming** profile. 1 GB of runtime belongs in Local, and the path is shorter. D-04 allows either location. Songs stay in `user://songs` (D-06).

### Pattern 1: Parts with pinned hashes (no network-supplied manifest)
**What:** `pack_spec.gd` holds the exact part list. The game never trusts a downloaded manifest. A part counts as installed when its hash was verified and it was extracted. `installed.json` records the verified part hashes, so if a later game version changes only the `app` part, only about 0.2 MB is downloaded again.
**Why parts:** `HTTPRequest` deletes a partial `download_file` on failure or cancel (http_request.cpp, `if (!download_complete) DirAccess::remove_absolute(download_to_file)`), and it opens the file with `FileAccess::WRITE`, so there is no Range resume [VERIFIED: 4.7-stable source]. Parts of about 100-165 MB limit the loss from a dropped connection. GitHub allows up to 2 GiB per asset and 1000 assets per release [CITED: docs.github.com about-releases]. The repo is public, so downloads need no auth [VERIFIED: GitHub API `"visibility": "public"`].
**Each part zip:** fewer than 65535 entries and under 4 GiB, so no Zip64 (ZipExtractor refuses Zip64). Forward-slash names. The builder writes it deterministically with Python `zipfile` (ZIP_DEFLATED); `Compress-Archive` is not used for this.

### Pattern 2: Download → verify → extract (Godot)
```gdscript
# Source: Godot 4.7 HTTPRequest / HashingContext docs; existing ZipExtractor
var http := HTTPRequest.new()
http.download_file = dl_dir.path_join(part.name + ".part")
http.download_chunk_size = 1 << 20          # 1 MB chunks (default 64 KB)
http.max_redirects = 8                      # GitHub 302 -> release-assets host
http.body_size_limit = part.size + 1024     # refuse anything larger than pinned
http.accept_gzip = false                    # raw bytes only
http.timeout = 0.0                          # no total timeout; own stall timer (no bytes for 30 s -> cancel_request + retry)
add_child(http)
http.request(PackSpec.url(part))
# progress: http.get_downloaded_bytes() / part.size every frame
# on RESULT_SUCCESS and code 200: hash on a worker thread
func _sha256_file(path: String) -> String:
	var ctx := HashingContext.new()
	ctx.start(HashingContext.HASH_SHA256)
	var f := FileAccess.open(path, FileAccess.READ)
	while f.get_position() < f.get_length():
		ctx.update(f.get_buffer(1 << 20))
	f.close()
	return ctx.finish().hex_encode()
# mismatch -> delete file, show "Download was corrupted, retry"; never extract
```
Extraction: copy ZipExtractor's approach (`_central_sizes` pre-scan with caps, `safe_rel` rejects `..`, absolute paths, drive colons and control chars). Do not use the song extension allow-list. Allow every name, because the hash already pins the content; the path checks are defence in depth. Write into `staging/`, then `DirAccess.rename_absolute(staging, v1)`. Write `installed.json` last. Run it on `WorkerThreadPool`. With about 25k files, expect tens of seconds; Windows Defender scans each new DLL. Show "Installing... n / N files".

### Pattern 4: Child process from Godot (D-05)
```gdscript
# Source: Godot 4.7-stable platform/windows/os_windows.cpp + drivers/windows/file_access_windows_pipe.cpp
var info := OS.execute_with_pipe(py_exe, PackedStringArray([
		"-I", "-X", "utf8", "-u", app_dir.path_join("autochart.py"), "job", job_json]), false)
if info.is_empty(): _fail("Could not start the autocharter"); return
_pid = info["pid"]; _stdio = info["stdio"]; _stderr = info["stderr"]   # KEEP _stdio alive: closing it = EOF = child exits
func _process(_d: float) -> void:
	_drain(_stdio, _out_buf)          # read only what is available: n = pipe.get_length(); pipe.get_buffer(n)
	_drain(_stderr, _err_buf)         # always drain stderr too (Python redirects it, native noise may still arrive)
	for line in _take_lines(_out_buf): _on_event(JSON.parse_string(line))
	if not OS.is_process_running(_pid):
		_drain(_stdio, _out_buf)       # final drain, then stop polling (a drained, broken pipe logs one engine error)
		_finish(OS.get_process_exit_code(_pid))
func cancel() -> void:
	OS.kill(_pid)                     # TerminateProcess on this PID only
func _notification(what: int) -> void:
	if what == NOTIFICATION_WM_CLOSE_REQUEST or what == NOTIFICATION_PREDELETE:
		if _pid > 0 and OS.is_process_running(_pid): OS.kill(_pid)
```
Verified facts:
- `execute_with_pipe` uses `NORMAL_PRIORITY_CLASS | CREATE_NO_WINDOW`, so there is no console flash.
- Pipes are `CreatePipe(..., 0)`, which uses the default (small) buffer.
- Non-blocking mode sets `PIPE_NOWAIT`.
- `get_length()` = `PeekNamedPipe` bytes available.
- `kill` = `TerminateProcess` (no process tree).
- The child inherits Godot's environment and current directory. That is safe with `-I`, because the cwd is not on sys.path.
- `create_process` has no pipes, so use `execute_with_pipe`.

### Anti-Patterns to Avoid
- **Free text on argv:** Godot's `_quote_command_line_argument` only wraps an argument in quotes when it contains a space or one of `&()[]{}^=;!'+,`~`. It does not escape `"` or trailing backslashes. Keep names in job.json, and never pass a path that ends in `\`.
- **`subprocess` inside the job** (today's `separate.py` runs `python -m demucs`): `OS.kill` cannot reach grandchildren, and a killed parent leaves demucs running.
- **Calling `get_line()` on a blocking pipe in `_process`:** it freezes the game until the child prints. Use `get_length()` + `get_buffer()`.
- **Dropping the `stdio` FileAccess reference while running:** it closes the stdin write end, and the watchdog kills the child.
- **Downloading into `user://songs` or extracting next to the exe:** use the pack root only.
- **Trusting a downloaded manifest for hashes:** hashes live in the game build.
- **`Compress-Archive` for the pack:** slow on large inputs and has historically stored backslash separators; use Python `zipfile`.

## Common Pitfalls

### Pitfall 1: stderr pipe fills and the child hangs
**What goes wrong:** The progress bar freezes at "Separating" forever.
**Why:** `CreatePipe(..., 0)` gives a small default buffer. demucs/tqdm, numba and torch warnings write to stderr. If Godot does not drain it, the child blocks on write.
**Avoid:** Python `os.dup2` sends fd 2 to a log file at startup; `TQDM_DISABLE=1`; Godot drains both pipes every frame anyway.
**Warning sign:** CPU drops to 0 while the process is still running.

### Pitfall 2: stdout buffering and encoding
Python block-buffers stdout when it is a pipe, so use `-u` plus `flush=True`. `-I` implies `-E`, so `PYTHONIOENCODING`/`PYTHONUTF8` are ignored; pass `-X utf8` and emit ASCII-only JSON (`json.dumps` default `ensure_ascii=True`). Non-ASCII song names then survive as `\uXXXX`.

### Pitfall 3: Argument quoting on Windows
See the anti-pattern above. A user-typed name containing `" --force` would otherwise become a separate argument. Job JSON avoids this class of bug completely.

### Pitfall 4: Orphans after cancel or crash
`OS.kill` = `TerminateProcess` of one PID. The child "does not terminate when Godot terminates" (docs). Mitigations: everything in-process; a stdin-EOF watchdog; kill on `NOTIFICATION_WM_CLOSE_REQUEST`. Delete `work/<job>` only after `is_process_running` is false; Windows keeps file handles until the process is gone.

### Pitfall 5: Separation is not deterministic
demucs `shifts=1` applies a random 0-0.5 s shift (`random.randint`), and the CLI never seeds it. Two runs of the same song give slightly different stems, so onsets can move by a frame. Seed `random` (and `torch.manual_seed`) in the job. Judge pack parity by the **sync gate**, not by byte equality with committed charts. The thread count can also change float rounding.

### Pitfall 6: Merged-interpreter Basic Pitch parity
librosa 1.0 vs 0.11 (`librosa.load(sr=22050)` resampler default), numpy 2.5 vs 2.2, scipy 1.18 vs 1.15. **Wave 0:** run Basic Pitch both ways on the 4 stems of 2 songs and compare `bp_<stem>.json`. If they are identical, merge. If they differ, compare the downstream chart (lanes only use integer MIDI pitch) and decide. If the difference changes lanes, keep two interpreters.

### Pitfall 7: setup_venv.ps1 cannot bootstrap on this PC
It looks for `C:/Python314/python.exe`, then `py -3.14`. This PC has neither: `py --list` shows only 3.15-32, and build/autochart does not exist. The pack builder (and dev venvs) should bootstrap uv from the pinned GitHub zip (sha256 above) instead. This is a prerequisite for every Python task in this phase.

### Pitfall 8: Offline model loading
demucs 4.1.0 loads through `huggingface_hub.hf_hub_download("adefossez/HTDemucs", ...)` (demucs/hf.py). Without `HF_HUB_OFFLINE=1` and the full cache layout (`refs/main` + `snapshots/<rev>/`), it tries the network on every run. beat_this "final0" goes through `torch.hub.load_state_dict_from_url` into `TORCH_HOME/hub/checkpoints/beat_this-final0.ckpt`. Pass the absolute ckpt path instead. Test the pack with the network disabled.

### Pitfall 9: Antivirus / SmartScreen
Files written by Godot carry no Mark-of-the-Web, so python.exe launched by CreateProcess gets no SmartScreen prompt [ASSUMED]. Defender real-time scanning slows extraction of about 25k files and the first torch import. Show a "first run is slower" note. A false positive on python.exe in AppData is possible but uncommon [ASSUMED]; the error message should name the log and pack folder.

### Pitfall 10: Memory on long songs
The decode guard allows up to 1200 s. htdemucs output for 20 min is 4 stems × 2 ch × 52.9 M samples × 4 B ≈ 1.7 GB, plus model and work buffers. Cap player songs at 600 s (10 min) in job mode [ASSUMED: peak about 2-3 GB for 10 min]. Map `MemoryError` to "Not enough memory for a song this long".

### Pitfall 11: Main-menu index coupling
`DESCRIPTIONS[i]` is paired with `menu_buttons()[i]`. Gamepad/harness tests and focus wrap assume 7 items, so adding "Chart a Song" means updating the tests in the same plan.

### Pitfall 12: `get_space_left()` returns 0 when the query fails
Treat 0 as unknown: warn and continue. Otherwise every install is blocked on systems where the query fails.

static func take_lines(buf: PackedByteArray) -> Array:   # returns [lines: PackedStringArray, rest: PackedByteArray]
	var lines := PackedStringArray()
	var start := 0
	for i in buf.size():
		if buf[i] == 10:

			start = i + 1
	return [lines, buf.slice(start)]
