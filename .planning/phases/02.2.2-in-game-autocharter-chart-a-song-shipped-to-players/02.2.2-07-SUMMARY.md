## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] ProcessAdapter flooded the game log with PeekNamedPipe errors**
- **Found during:** Task 1, the first full run.
- **Issue:** `_drain` called `pipe.get_length()` (PeekNamedPipe) every frame. The job dup2s fd 2 into its log at startup, and that closes the stderr pipe's write end. From then on every `read_stderr()` logged `Condition "!PeekNamedPipe(...)" is true` plus a backtrace. That was about 18,000 log lines per e2e run, and in the shipped game it would be thousands of godot.log lines per chart. stdout failed the same way after each child exited.
- **Fix:** `_drain` now loops `get_buffer(64 KiB)` (pipes are PIPE_NOWAIT, so ReadFile returns what is there or nothing, with no engine error), capped at 4 MiB per call. A probe confirmed that partial reads and reads from broken pipes are non-blocking and silent. tests/test_process_adapter.gd covers a real cmd.exe child (stdout and stderr, 200 post-exit reads under 1 s) and a 4000-line burst across chunks. The re-run had 0 ERROR lines. ProcessAdapter's public API is unchanged, so the runner and screen tests are unaffected.
- **Commit:** c82f019

**2. [Rule 1 - Test correctness] The cancel check raced asynchronous process teardown**
- **Issue:** TerminateProcess is asynchronous. The runner sees the exit code at once and emits `cancelled`, but tasklist still listed the PID while Windows freed its memory (36 MB of 1.6 GB left). A single tasklist call failed the step.
- **Fix:** the harness polls tasklist every 0.1 s for up to 15 s and records `gone_after` (0.1 s, 1 poll). It also cancels 3 s into `separate` while torch is busy, rather than 0.3 s after the stage event when the interpreter has barely started. That is a stronger test of D-05.
- **Commit:** c82f019

**3. [Rule 3] Missing tests/test_pack_spec.gd.uid (from plan 06)**
- The headless `--import` that created the new .uid files also created this one. It is committed with Task 1. The `.import` files it touched were restored, not committed.
