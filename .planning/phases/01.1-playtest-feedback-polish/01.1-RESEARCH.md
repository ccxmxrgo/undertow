## Summary

Everything in this phase is code on top of a well-factored Phase 1 codebase; no new libraries or addons are needed. All drawing is `_draw()` based (Highway, Feedback, NoteShape); the one place a shader is justified is the visor overlay. Four non-obvious findings drive planning: (1) default keys live in TWO places (`BindingStore._defaults()` and `project.godot` `[input]`), and `Settings.save_to` writes every current key into settings.cfg, so any friend who ever changed a setting in v0.1 has D/F/J/K frozen in their file (D-01's "don't overwrite" means those players keep DFJK; see Open Question 1). (2) `ChartData` has no id field, so scores.cfg needs one added (`TestCharts` ids now). (3) Godot's `WINDOW_MODE_FULLSCREEN` is borderless on Windows, works with the existing canvas_items/keep stretch, and is the right choice; exclusive fullscreen is not needed. (4) The release export template is LARGER than debug (109.3 MB vs 103.2 MB for x86_64) and a Deflate zip of it is 38 MB, so `<30 MB` is only reachable with a `.7z` (LZMA2, measured 26.5 MB for the release exe) which the Windows built-in `tar.exe` can create. A plain `.zip` stays 34-38 MB.

**Primary recommendation:** Implement in four waves: (A) data/logic with unit tests (default keys, `ScoreStore`, chart id, milestone logic, window-state persistence, practice flag), (B) rendering (Palette lane colors, Highway/NoteShape/Feedback per-lane color + receptors + brightening, streak counter/popups), (C) visor shader + fullscreen/F11 + Settings rows + menu entries, (D) export/README/packaging with both a `.zip` and a `.7z`.

## Architecture Patterns

```

F11 / Settings toggle -> Settings.set_fullscreen(bool) -> apply_window() -> save_to() -> settings_changed
```

### Pattern 1: Window mode (POL-04)
Godot docs: `WINDOW_MODE_FULLSCREEN` is NOT exclusive; on Windows and Linux a borderless window is used to emulate fullscreen. `WINDOW_MODE_EXCLUSIVE_FULLSCREEN` is Windows-only [CITED: web search summary of docs.godotengine.org DisplayServer/Window class docs; forum threads]. Plain fullscreen intentionally leaves a 1 px line so Windows does not treat it as exclusive; this only matters for integer scaling, irrelevant to a 1920x1080 canvas_items/keep stretch [MEDIUM, forum-sourced]. Exclusive has real downsides (slow alt-tab, overlays/Game Bar/Discord do not work, snipping tool sees stale frame) [MEDIUM, forum]. No controlled latency benchmark exists; use borderless as D-06 specifies and verify with the existing frame probe if desired. Keep vsync as project default (do not change; Phase 1 clock work is calibrated to it) [ASSUMED: no vsync change needed].

```gdscript
# Settings autoload
var fullscreen: bool = true   # default per D-06
const WINDOWED_SIZE := Vector2i(1600, 900)

func apply_window() -> void:
    if DisplayServer.get_name() == "headless":
        return  # tests: DisplayServer is a dummy
    if fullscreen:
        DisplayServer.window_set_mode(DisplayServer.WINDOW_MODE_FULLSCREEN)
    else:
        DisplayServer.window_set_mode(DisplayServer.WINDOW_MODE_WINDOWED)
        DisplayServer.window_set_size(WINDOWED_SIZE)
        var scr := DisplayServer.window_get_current_screen()
        var origin := DisplayServer.screen_get_position(scr)
        var area := DisplayServer.screen_get_size(scr)
        DisplayServer.window_set_position(origin + (area - WINDOWED_SIZE) / 2)

func _unhandled_key_input / _input(event):  # F11, ignore echo
    if event is InputEventKey and event.pressed and not event.echo and event.keycode == KEY_F11:
        set_fullscreen(not fullscreen)
```
Notes: Call `apply_window()` at end of `load_from` (also from the `Settings._ready` path) so boot honors the saved value; consider also setting `display/window/size/mode` in project.godot to fullscreen (value 3) so the first frame is not a windowed flash (project setting then overridden by Settings if the user chose windowed) [ASSUMED mapping 3 = fullscreen; verify in editor]. Windowed size set right after a mode switch may be ignored on some platforms until next frame; if so use `call_deferred`. Low risk. `window/size/window_width_override`-style settings are not needed. Reading the real current mode (user dragged/maximised) is not required; persist only the bool. F11 is free: F3 = debug_overlay (4194334), F4 = debug_autoplay (4194335); F11 must not be offered to the rebind UI (it is not a gameplay action, so it is not).

### Pattern 2: Visor frame (POL-02 / D-03)
One `ColorRect` (full rect, `mouse_filter = IGNORE`) with a canvas_item shader that outputs only alpha-blended black/green: vignette (smoothstep on distance from center, slightly squared for a rounded-rect feel), faint scanlines (`sin(FRAGCOORD.y * k)` low amplitude), optional rounded-corner mask. Needs no `hint_screen_texture`, so no back-buffer copy and cheap on the Compatibility renderer [HIGH: pure alpha overlay is standard canvas_item behavior]. Corner brackets and small edge readouts (e.g. "DEPTH", "SONAR") are cheaper as `_draw()` polylines in a Control than in the shader. Low-effects toggle: `Settings.low_effects` (bool, persisted) hides scanlines and/or the whole shader rect; also honor `reduce_motion` by never animating it. Place it ABOVE Highway/Feedback/Hud but BELOW pause/results/fail overlays so menus stay readable (add in `Gameplay.start` before `_on_run_built` overlays, or order children accordingly). Use `UiLayout.fill_rect` (not PRESET_FULL_RECT) per the existing playtest-gap-1 lesson. Keep opaque coverage out of the lane region (vignette alpha near 0 within the highway) so notes are not darkened; the receptor/hit area at y=880 of 1080 sits near the bottom edge, so cap bottom vignette strength.

Shader sketch:
```glsl
shader_type canvas_item;
uniform float vignette : hint_range(0.0, 1.0) = 0.55;
uniform float scan : hint_range(0.0, 0.2) = 0.06;
void fragment() {
    vec2 p = UV * 2.0 - 1.0;
    float v = smoothstep(0.55, 1.25, length(p * vec2(0.9, 1.0)));
    float s = 0.5 + 0.5 * sin(FRAGCOORD.y * 3.14159);   // 2 px period
    COLOR = vec4(0.0, 0.0, 0.0, clamp(v * vignette + s * scan, 0.0, 1.0));
}
```
Scanline moire risk under canvas_items stretch at non-1080p resolutions: use UV-based line count (`UV.y * 540.0`) rather than FRAGCOORD so it scales with the stretched canvas.

### Pattern 3: Per-lane colors + brightening + receptors (POL-02/03)
- `Palette`: add `const LANE_COLORS: Array[Color]` (cyan/amber/magenta/lime from D-02) and `static func lane_color(lane) -> Color`. Keep `ACCENT` for hull line, borders, HUD.
- Highway `_draw_notes`: replace `Palette.ACCENT` with `Palette.lane_color(lane)`. Compute `dt = float(n["time"]) - vt` (note: Highway uses `vt = st + Settings.visual_offset`; judgment uses song_time, so for "ready" state use judge time `st`-based dt to match the actual window, i.e. `in_window = absf(float(n["time"]) - st) <= good_window`; the visual position uses `vt`. This keeps brightening honest even with visual offset) [reasoned from source]. Need `good_window`: Highway currently has no JudgeConfig; pass `cfg` through `setup()` or read `JudgeConfig.new().good_window` once (Gameplay creates `cfg` locally, so add an optional param to `highway.setup`). Dim = `col.darkened(0.45)` / multiply RGB by 0.55 keeping alpha 1 (do NOT reduce alpha, `NoteShape` fills at 25% of alpha and the note would look transparent over lane lines). In-window: full color + extra glow (second outline 6 px wider at alpha 0.35, or an outer `draw_arc`/polygon scaled 1.15).
- Sustain tails: `_draw_sustain` gets the lane color; dim until head is in window or while holding.
- Receptor: draw `NoteShape.draw(self, kind, Vector2(cx, HULL_Y), SIZE, lane_color)` with fill alpha 0 variant (add an `outline_only` param or pass a color with small alpha); pulse = scale 1.0 to 1.2 and brighter for ~120 ms after `LaneInput.lane_pressed`. Highway needs a per-lane `_press_ticks` array and a `on_lane_pressed(lane, ticks)` hook connected in `Gameplay.start`. Receptor must be drawn AFTER notes so notes pass under/over consistently; draw before the hull line segment or after, pick after for visibility.
- Feedback: flash rect, ring, and floating-text color for Perfect/Good use lane color; `MISS` stays `DESTRUCTIVE`. Feedback's text colors (PERFECT = ACCENT, GOOD = TEXT) can stay (judgment identity), only flash/ring use lane color per D-02.
- Check contrast of the four colors on `#000000`/`PANEL`: all four are bright (>7:1 on black) [ASSUMED, quick mental check; verify via screenshot in playtest harness]. Amber vs lime can be close for some color-blind users; shapes remain the second channel (already guaranteed by D-24).

### Pattern 4: scores.cfg (POL-05 / D-07)
Reuse the Settings pattern exactly: `ConfigFile.parse(text)` from `FileAccess.get_file_as_string` (never ResourceLoader), type-check and clamp every value, on parse error back up to `.bak` and start empty, atomic save via `path + ".tmp"` then `DirAccess.rename_absolute`. Schema:

```
[chart:hand_chart_v1]      ; section name = chart id (sanitized: [a-z0-9_.:-], max 64 chars)
best_depth=123.4           ; float, clamp 0..1e7
best_accuracy=96.5         ; float %, clamp 0..100
max_combo=42               ; int, clamp 0..1e6
date="2026-10-08"          ; string, max 10-32 chars, validated by regex or just truncated
```
Independent bests per field (depth best and accuracy best can come from different runs) OR whole-record keyed on depth: recommend independent per-field maxima plus "NEW RECORD" defined strictly as `depth > previous_best_depth` (what D-07 says: "when the score is beaten"). Accuracy = `(perfect + good) / total_notes` or weighted (perfect=1, good=0.5)? Pick one and test it; recommend `(perfect + good) / (perfect + good + miss) * 100` with 0 notes => 0. Eligibility is a pure function: `not autoplay_used and not score.no_fail_used and not practice and not Settings.no_fail`. Subtle: with the global Settings.no_fail ON, `score.no_fail` is true but `no_fail_used` only flips when hull hits zero; a flawless no-fail run would still count unless you test `score.no_fail` itself. Recommend `eligible = not (autoplay_used or score.no_fail)` which is stricter and matches D-07 "No-Fail runs never count". Failed runs (state FAILED) never reach `_finish`, so they never submit; keep it that way (D-07 says best depth; a fail screen exists with depth, but recording failed dives is out of scope unless desired - flag below).

Chart id: `ChartData` has no id. Add `var id: String = ""`, set in `TestCharts.hand_chart()` (`"test.hand_chart.v1"`), and in `short_chart`/`click_chart` likewise; Phase 2 will set it to a content hash [reasoned]. Bump the suffix if the hand chart's notes change so old scores do not apply. Unit tests: round trip, corrupt file, wrong types, NaN/inf, huge values, missing section, ineligible run does not write, new-record boundary (equal is not a record).

### Pattern 5: Streak counter + milestones (POL-06)
`HullScore` already exposes `combo_changed` and `streak_changed` (perfect streak). D-08 says "note streak" and keeps HUD "Perfect streak and combo". The friend's "note streak" most plausibly means consecutive hits = **combo** (resets on miss/stray, continues through Good). Recommend the big counter and milestones use `combo`, labeled "STREAK" (UI copy), leaving the HUD perfect-streak row as is [ASSUMED; confirm, see Open Questions]. Pure helper `StreakMilestones.reached(old, new) -> int` returning the milestone crossed (10, 25, 50, 100, 200, ...); combo increments by 1 so a simple `is_milestone(n)` check suffices, but `reached` guards against skipped values (sustain ticks do not change combo). Popup: text "25 STREAK" in a lane-neutral color (`Palette.ACCENT` or `TEXT`), drawn centered above the highway (y ~ 500-600), 700 ms ease-out rise+fade; under `reduce_motion` no rise or scale, just a fade (or static 700 ms). Big counter: Label/`draw_string` at Highway center above hull line (y ~ 760), font size scaled `lerp(SIZE_HEADING, SIZE_DISPLAY, clamp(combo/100,0,1))`, outline/glow alpha grows with combo; hide when combo < 5 to avoid clutter. Do not place it over the lane where notes land (it will obscure notes); put it above the highway top or to the side of the lanes, or draw it at low alpha behind notes. Recommended: left of the highway at x ~ lane_left - 200 (there is wide empty space at 1920 width) or in the visor frame's top bracket. Pop animation on each increment can use Hud's existing `_pulse`.

### Pattern 6: Practice entry (POL-07 / D-09)
`MainMenu._build` creates items via `_item`; insert `practice_button` after `start_button` and add it to the `items` focus ring (focus ring is built from that array, easy to miss). Add `static var pending_practice: bool` to `Gameplay`; in `start()`: `score.no_fail = Settings.no_fail or practice`. Restart/retry must preserve practice (store `practice` member like `autoplay`), including the F4 restart and `_on_retry`. `launch(autoplay)` signature is used by tests (`test_menu_flow`); add `launch_practice()` rather than changing it. Results screen: show a "PRACTICE" flag line and suppress record UI.

### Anti-Patterns to Avoid
- Changing `Settings.no_fail` for practice (it would persist and silently disable records afterwards).
- Putting records in settings.cfg (D-07 says separate; also `reset_defaults()` would wipe them).
- Reducing note alpha to dim (breaks the 25% fill look); scale RGB instead.
- Drawing the visor with a screen-texture shader (needs a BackBufferCopy, costs fill-rate, unnecessary).
- Using exclusive fullscreen (breaks overlays/alt-tab, no proven latency win).
- Reading `Settings.visual_offset`-shifted time for the "ready" test (use judge time).

## Common Pitfalls

### Pitfall 1: Default keys in two places, plus frozen saved keys
**What goes wrong:** Changing only `BindingStore._defaults()` leaves `project.godot` `[input] lane_1..4` at physical_keycode 68/70/74/75; `BindingStore` overrides at runtime, but anything reading InputMap before `Settings._ready` (and the tests in `tests/test_input_mapping.gd`/`test_bindings.gd`, which assert `KEY_D`) differs. Also v0.1 settings.cfg files carry explicit D/F/J/K.
**How to avoid:** Change both places (KEY_1=49 .. KEY_4=52; edit `physical_keycode` in project.godot for lane_1..4), update every `KEY_D/F/J/K` assertion in `tests/test_bindings.gd` (lines ~38, 89, 113, 185, 208, 216) and any rebind test that binds `KEY_D`. Add tests: fresh defaults are 1-4; a cfg with explicit saved `lane_1_key = KEY_Q` stays Q; reset gives 1-4.
**Warning signs:** Playtest friend still on DFJK; label under lanes shows "D".

### Pitfall 2: Duplicate resolution with mixed old/new keys
`_resolve_duplicates` reverts a customized key to its (new) default if it collides. A player who saved lane_1 = KEY_2 (custom) and defaults 1,2,3,4 now collide: lane_2's default "2" vs lane_1's custom "2": the code reverts the custom/non-default entry (`b` first if it differs from its default). Behavior is safe (no duplicates) but could silently rebind a saved choice. Add a test for the collision outcome and accept it.

### Pitfall 3: Number keys and the number row on non-US layouts
Physical keycode `KEY_1` is the physical top-left digit position regardless of layout (AZERTY digits need Shift for glyph, but the physical key still fires) [CITED: project D-01 intent; Godot physical_keycode semantics]. `display_name` uses `as_text_physical_keycode()` which shows "1".."4". Numpad digits are different keycodes (`KEY_KP_1`); not bound by default.

### Pitfall 4: Windowed mode after fullscreen on boot
Setting size before the mode change gets discarded; set mode first, then size/position. Headless test runs: guard `DisplayServer.get_name() == "headless"`; do not launch windowed Godot in tests. Settings tests that call `load_from` must not require a real window.

### Pitfall 5: Brightness switch flicker at the window edge
Evaluating `abs(dt) <= good_window` per frame is fine, but a note that was dim, goes bright inside the window, then is judged: after a Good/Perfect it is `S_HIT` (not drawn); after a miss it draws as MISSED at 25% alpha. No state bug, but ensure the S_MISSED path still uses lane color at 0.25 alpha. Notes whose window is already passed without a hit are `S_PENDING` until `InputJudge.tick` marks them missed at `good_window` + (see `early_miss_window` 0.1): between 0.070 and 0.100 s late they are drawn dim again (correct, they are no longer hittable).

### Pitfall 6: Records written on non-finishing paths
`_finish` is the only path to results; fail screen path must not submit. Autoplay F4 restart sets `autoplay_used` for the whole Gameplay instance (never resets), which correctly makes the rest of the session ineligible; keep using `autoplay_used` (not `autoplay`). Also add `practice`.

### Pitfall 7: Release template is larger, zip stays > 30 MB
Measured locally [VERIFIED]: `windows_release_x86_64.exe` 109,268,480 B vs `windows_debug_x86_64.exe` 103,176,704 B. Deflate zip of release exe: 38.07 MB; v0.1 debug zip 34.66 MB (so debug zips smaller than release!). `.7z` (LZMA2 via Windows `tar.exe --format 7zip`) of the release exe: 26.50 MB; xz -9e estimate 26.46 MB. So: `--export-release` is OK to use (no debug overhead at runtime; and `.pck` is tiny, 183 KB) but does not reduce zip size. To get under 30 MB ship `UNDERTOW-playtest-v0.2.7z` (recipient needs 7-Zip, which Windows 11 24H2+ Explorer can also extract natively [ASSUMED, libarchive support added in Win11 23H2/24H2]) in addition to the compatibility `.zip` (~35-38 MB). Decision needed from user: D-10 names the file `.zip`. Smaller custom export templates (`disable_3d`, module stripping) require building Godot from source: out of scope.

Excluding the console exe: set `debug/export_console_wrapper=0` (currently 1 in export_presets.cfg) - saves only 189 KB; the real saving is none. Embedding the pck (`binary_format/embed_pck=true`) gives a single exe, simpler for friends; size roughly the same. Release builds drop the debugger and `print` still works; `push_warning` goes to log. Keep the console build only if friends need logs (undecided; recommend a single embed-pck release exe plus README line on where logs go).

### Pitfall 8: Export filter
`export_presets.cfg` has `include_filter="*.json,*.cfg"` and excludes `addons/*`. New `res://shaders/*.gdshader` files are exported automatically (resources referenced by scenes/`load()`); if the shader is loaded with `load("res://shaders/visor.gdshader")` from script only, the exporter still includes it since `export_filter="all_resources"`. Good. scores.cfg lives in `user://`, not exported.

### Pitfall 9: Visor over UI
A full-rect ColorRect with default `mouse_filter = STOP` eats clicks; set IGNORE. Overlaying the pause menu would darken buttons; order the visor below overlays.

## Open Questions

1. **Migration of v0.1 saved D/F/J/K**
   - Known: `to_config` writes every key on any save, so friends who touched any setting (including calibration, which saves) have `lane_*_key` = D/F/J/K explicitly. D-01 forbids overwriting saved bindings, so literally they stay on DFJK and "make 1234 default" fails for exactly the friend who asked.
   - Recommendation: add a `bindings_version` int to `[bindings]`; if the file has no version AND all four lane keys exactly equal the old defaults (D,F,J,K), treat them as defaults and migrate to 1-4 once (then write version 2). Any other saved set is preserved. Ask the user to approve this narrow exception; otherwise document in README "press Reset Controls".
2. **Failed runs and records:** only completed dives record (a fail never reaches results). Confirm that is acceptable, or record best depth from the fail screen too (`score.depth()` is available there).
3. **Zip vs 7z for the <30 MB goal** (Pitfall 7): need user choice of ship format.
4. **Streak = combo vs perfect streak** (A1).
5. **Menu best-score display:** recommend a Label under Start Dive: "Best: 123 m  96%". Chart id for the menu is `TestCharts.hand_chart().id` (the only chart now).

|----------|---------|---------|

### Threat Patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Malformed/oversized scores.cfg | Tampering/DoS | defensive parse, cap number of sections processed (e.g. 256), `.bak` on parse error |
| Section name injection (`]`, newlines in chart id) | Tampering | sanitize ids to a safe charset before use as a section name |
| Path traversal | Tampering | fixed path `user://scores.cfg`, no user-supplied paths |
| Hand-edited scores | Repudiation | accepted risk; local-only |
